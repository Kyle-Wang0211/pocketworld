# Design

## Sources of K and their pixel reference

| Path | Source | Reference (official) | Pushed pixels | Conversion |
|---|---|---|---|---|
| iOS zero-ARKit ON arm | `kCMSampleBufferAttachmentKey_CameraIntrinsicMatrix` | CMSampleBuffer.h:1849-1857 (iPhoneOS26.2.sdk): "applied to the current sample buffer ... The origin is the upper left of the frame." | that sample buffer's own BGRA image buffer, full size | none |
| iOS ARKit shadow | `ARFrame.camera.intrinsics` | ARCamera.h:54-69: pixels, "The origin is at the center of the upper-left pixel", reference `imageResolution` | plane 0 box-d downsampled to 640x480 | `fx/d, fy/d, (cx+0.5)/d-0.5, (cy+0.5)/d-0.5` |
| Android (TODO) | `CaptureResult.LENS_INTRINSIC_CALIBRATION` | AOSP CaptureResult.java: pre-correction active array, pixel (x,y) center at (x+0.5, y+0.5) | output stream after crop region + centered aspect crop + scale | not implemented |

The ON-arm buffer is the sample buffer itself, so no rescale is needed. The
Apple documentation does not state what happens to the matrix when the video
output scales the buffer (`videoSettings` size != active format size).
`PwCameraSlot.start` requests `videoSettings` equal to the active format, so the
two readings coincide; at run time each frame is checked (pushed buffer ==
sample-buffer format description == active format dimensions) and any mismatch
falls back to the YAML K with a counted reason instead of guessing a rescale.

The ARKit shadow rescale uses the pixel-center-at-integer convention that
ARCamera.h states. It is implemented once, in C++, and pinned by a fixture
generated by running the real converter on recording `run-6e2d4b99`
(120 frames, max abs difference 0).

Android's documented convention is the pixel corner convention and its
reference is the pre-correction active array, so the ARKit formula must not be
reused as-is. The mapping also depends on `SCALER_CROP_REGION`, the centered
aspect crop, `CONTROL_ZOOM_RATIO`, `SENSOR_PIXEL_MODE`, and on
`LENS_DISTORTION` when correction is off. It cannot be verified without a
device, so the Kotlin entry takes K in pushed-buffer pixels and callers pass
`null` until that mapping is implemented and checked.

## Transport contract

- `k == NULL` (and every rejected K) builds exactly the legacy `XRSLAMImage`
  (zeroed, `ext == NULL`, `ext_size == 0`) and issues exactly the legacy call
  sequence (push, run, state, camera pose). A cross-binary dump against the
  pre-change transport (cfe7d44) is byte-identical.
- A valid K attaches a zeroed 72-byte extension with the four values,
  `has_intrinsics = 1`, `ext_size = 72`. Validity = the fork's own acceptance
  rule (finite, fx > 0, fy > 0), so the transport never attaches something the
  engine would silently ignore.
- After a K push the transport reads `XRSLAM_INFO_INTRINSICS` once. The fork
  reports the latest per-frame K; an unmodified core reports its YAML K. The
  ledger counts `engine_report_matched`, so a run on the wrong archive is
  visible as "attached but not consumed".

## Engine archive

`libxrslam_gpufenothread_pfk_6f6aa21c.a` = the gpufe_nothread recipe
(`build_gpufe_nothread.sh`, sha256 f0e5ae35...) on a clean clone of 04c0e83.
Two clean builds at the same paths are bit-identical. A control build of
8a1cc12 (parent arm) at the same source and build paths differs in exactly
`XRSLAMManager`, `detail`, `opencv_image`, `gpu_image`,
`XRGlobalLocalizerManager` and the symbol table; the other 52 members are
byte-identical.

## Bench A/B (defined here, not run in this change)

- Arms: `-PWPerFrameIntrinsics on` vs `off`, same engine archive
  (`gpufenothread_pfk`), same capture copy, same device.
- Required record per run: arm label, switch source, `transport_attached`,
  `transport_engine_report_matched` (must equal attached in the on arm),
  `transport_not_attached` with host reasons, fx min/max, pushed resolution.
- A run whose on arm has `engine_report_matched < attached` is invalid (wrong
  archive linked).
- Per `AGENTS.md`, only the physical-phone production pipeline can select a
  production default; host replays stay diagnostic.
