# 5–10× 归档缩减：全球调研判决与改进方案

> 日期：2026-08-04
>
> 触发：用户要求把 1.37× 的严格无损冷归档提升到 5–10×。
>
> 证据来源：8 路并行调研 + 2 路对抗验证（222 次检索），全部出处内联；
> 本仓库既有冻结实验数据（worldpack / lepton_jxl_iphone / plr_derived_brunsli_two_photo）。

## 一、判决：目标与手段必须分家

### 1.1 对已有 JPEG 字节做 5–10× 严格无损 —— 不可行（对抗验证 CONFIRMED）

需求侧：638,645,632 B 项目 5× = 预算 127.7 MB；照片 155 × ~2.79 MB ≈ 432 MB，
即便数据库/PLY/sidecar 全部归零，照片也要削减 ≥70.4%。

供给侧（全球已发表最好水平，验证者逐表核对）：

| 方法 | 对 JPEG 字节削减 | 出处 |
|---|---:|---|
| Lepton | 19.5–26%（本项目实测 20.8%） | arXiv:2308.13287 Table 1 |
| JPEG XL 转码 | 14.3–22.7%（本项目实测 17.9%） | 同上 |
| CMIX（万倍慢） | 23–30% | 同上 |
| CVPR2022 MLCC | 29.5–32.6% | arXiv:2203.16357 |
| **单图 SOTA（字节跳动 ICIP 2023）** | **34.06% (4:2:0) / 35.57% (4:4:4)** | arXiv:2308.13287 |
| 跨照片集合（微软 TIP 2016） | >31%，**纯跨图增益仅 ~8–10 个百分点** | ieeexplore 7448441 |

把 SOTA 35% 套满：照片 432→281 MB，全项目天花板 **638/281 ≈ 2.27×，不足 5× 的一半**。
需要的 70% 是已证实上限的 2 倍，且该方向单图 22%→35% 走了十年、跨图 2016 年后停滞。

修正记录（验证者对我此前说法的纠正）：
- "34% 是病理专用模型"不准确——34.06%/35.57% 是通用模型在自然图像上的成绩，SOTA 比我说的还高，但结论不变；
- "量化噪声照片间独立"措辞不严谨——独立的是散粒/读出噪声与亚像素错位被各帧独立量化的部分，条件熵地板机理不变；
- 无信息论 converse 证明，属实证/工程不可行，决策上按不可行处理。

LMCompress（Nature MI 2025）像素域无损即使翻倍 JPEG XL 也是 ~7.5 MB/帧 > 现有 2.8 MB，
且不重建 JPEG 字节，与本任务无关。DiffC 类扩散编码是有损，不适用。

### 1.2 5–10× 在哪里

照片是自己的 App 拍的。0.3 秒间隔的时域冗余现在被逐帧独立 JPEG 在有损量化**之前**切断——
Apple 自己的管线也不利用它（HEIC 静态照片是 512×512 tile 纯 intra，连拍历史上直接存 JPEG，
HEIF 规范里带 inter 的 heics 序列 Apple 从未在相机管线启用；nokiatech.github.io/heif/technical.html、
WWDC17 Session 513）。把编码时机移到量化之前，"严格无损"的锚点自然移到采集写盘的码流上。

## 二、修正后的倍数账本（对抗验证 PARTIAL——我最初的 3–8× 被砍到 2–4.5×）

验证者拆解（全部有出处）：
- intra 因子 ≈ 2×：iPhone 实测 HEIC ≈ JPEG 的 1/2；RealityScan 1.1 从 JPEG 切 HEIC 官方宣称缩 50%；
- inter 因子 ≈ 1.9–2.7×：Nokia HEIF 官方 Table V 的 burst 类实测（我此前引用的 4.8× 混入了 cinemagraph 离群类）；
  MV-HEVC 对实拍立体仅省 15–20%，大视差时 5–15%；
- VideoToolbox 硬编的率失真效率显著差于参考编码器（M1 实测需 ~7× 码率才追平 libx265 crf28 的可用质量），
  文献增益数字不能直接套硬编；
- 质量等同前提未经验证：压缩会使 SIFT keypoint 在 7×7 窗口内漂移，QP<32 才多数不变（APSIPA 2016）；
  ScanNet 特意用 0.4 bpp@30fps 防伪影，而 30fps 视频的时域相关性是 0.3s 间隔 burst 的 ~9 倍。

**修正后可信区间：照片字节 2–4.5×（中心 2.5–4×）**；更高倍数 = 动用画质预算，必须过重建 parity 门才许可。
文献侧的宽容度锚点：JPEG 压缩比 <10:1 不伤摄影测量精度（PE&RS 2002）；VOCA 显示退化是渐进非悬崖。

### 全项目组合账本

| 方案 | 照片 | 全项目 | 倍数 | 性质 |
|---|---:|---:|---:|---|
| 现状（Lepton+ZPAQ 归档） | 342 MB | 467 MB | 1.37× | 已实测 |
| A：榨干现有 | ~330 MB | ~455 MB | ~1.4×（天花板 1.65×） | 旧项目唯一手段 |
| C-lite：HEIC 直切（RealityScan 同款） | ~216 MB | ~422 MB | 1.5× | 竞品已出货验证 |
| C-lite + B（再生） | ~216 MB | ~223 MB | **2.9×** | 低风险组合 |
| C：HEVC GOP 保守 2.5× + B | ~173 MB | ~180 MB | **3.5×** | 探针+parity 门后 |
| C：HEVC GOP 验证 4× + B | ~108 MB | ~115 MB | **5.5×** | 中心情形 |
| C：GOP + 画质预算（过 parity 门） | ~62 MB | ~69 MB | **9.2×** | 上限情形，逐级验证 |

B = 派生数据确定性再生：DB 199 MB + PLY 不入冷归档，存种子+代码版本+校验，
需要时逐位重放。可行性依据：本仓库 GPU matcher 已做到 15/15 位级一致；SfM 有固定 seed。
需要用户签决解除冷归档合同中"不删可再生模块"条款，替换为"可证明再生 + 抽查校验"。

**结论：5× 的下沿由 C+B 无损（按新锚点定义）覆盖；接近 10× 需动用经 parity 门验证的画质预算。**

## 三、Track C 设计要点（全部来自查证，含对抗验证的修正）

### 3.1 编码器选型：VideoToolbox / MediaCodec 硬件 HEVC，别无分店

- iPhone 无任何一代 AV1 硬件编码（A17 Pro 起仅硬解；Apple 新闻稿 + Meta 2025 白皮书 Table 2）。
  软编 AV1 与热约束冲突，排除。
- 硬件 HEVC 亚瓦级（Ambarella 整片 4Kp30 <1.4W 含 ISP），本用例吞吐仅 4K30 录像的 **13%**
  （4224×2376@3.3fps ≈ 33.4M luma/s vs 248.8M/s）——是全设备最热友好的压缩器，
  但必须进既有热压测 harness 做 A/B（采集期已同时跑相机+ARKit+GPU SIFT）。
- 无损 HEVC 硬件不存在（VideoToolbox 无 RExt 入口），方案按有损设计画质预算。
- all-intra 与 inter GOP 都是一级 API（AllowTemporalCompression / MaxKeyFrameInterval）。
- 质量控制是码率制（AverageBitRate/DataRateLimits），iOS 上无恒定质量承诺——画质预算按每场景码率标定。

### 3.2 分辨率：Level 6 探针是全案第一个硬门

4224×2376 = 10,036,224 luma 样本 > Level 5.2 上限 8,912,896 → 强制 Level 6 码流。
- A17 Pro/A18 有存在性证明（LumaFusion 5.4 起 iPhone 15 Pro/16 系开放 5K–8K HEVC 导出）；
- **A14–A16（机队主体）是空白**，且历史上有 4K 墙先例（T2 Mac、LumaFusion 旧版 iOS 锁 4K）；
- 探针必须在支持机队的**最老档位**跑，不是开发机；
- 兜底尺寸修正（验证者抓到的算术错误）：4032×2268 仍是 Level 6；
  真正 L5.x 安全：**4096×2176（恰好压线）、4096×2160、3840×2160**，或双流切片 2112×2376。

### 3.3 专利与许可（对抗验证后的净结论）

- 系统 API 路径干净：Access Advance 应税对象是"随设备/软件安装的编解码器"，App 调用 OS 编码器不安装任何实现；
  叠加 Quanta v. LG 专利穷竭。十年零 App 开发者被追索先例（Blackmagic Camera、LumaFusion 常年在架）。
  注意：这是许可结构推论，无池方明示豁免文书。
- **Android 兜底红线：绝不能用软件 HEVC 编码器兜底**（App 即成应税产品）。兜底 = 硬件 H.264 或保留 JPEG。
- x265 = GPL + 专利双雷，永不内嵌。SVT-AV1/libaom/rav1e 版权面干净（BSD + AOM 专利授权）但 iOS 无硬编，仅留作
  Android AV1 白名单（Tensor G5/Pixel 10 已实用化）远期增强。
- 2026-01 起 Access Advance 设备费 $0.24；HP/Dell 熔断硬解、Nokia 德国禁售令——全是设备级动作，
  但预示低价 Android 设备可能出厂关 HEVC：MediaCodec 运行时探测从"建议"升为"必须"。
- FFmpeg LGPL 构建有条件可用（VLC 先例）；FFV1 帧内无损不吃时域冗余，与目标无关。

### 3.4 重建质量门（决定倍数上限的门）

文献现状：ScanNet H.264@15Mbps、CO3D 1.9 万段手机视频过 COLMAP、Tanks&Temples 4K30——
"有损视频帧上做大规模重建"有工业先例；但 **"CRF/码率 vs 重建精度"没有直接文献，是空白**，必须自测。

门的设计（复用既有仪器）：
1. E24 黄金基线 ce78a8f 的采集帧，离线转码为候选码率阶梯（intra-only 与 GOP=8 各一组）；
2. 全管线重跑 SfM/MVS，对比：配准率、轨迹长度、重投影误差、稠密点数、compare.html 并排肉眼对比（用户批准制）；
3. 风险监控项：keypoint 亚像素漂移（QP≥32 危险区）、运动模糊帧、卷帘快门、自动曝光跳变；
4. 每级码率一个 parity 结论，取"通过的最低码率"为画质预算，不外推。

### 3.5 随机访问与产品约束

- GOP=8 恰好等于既有 Phase 5 设计的 4/8 图依赖组，随机读一张最多解 8 帧；
- 300 帧全解码缓存 ≈ 9 GB，超手机内存——导出/重跑需 GOP 感知调度或临时重物化，计入设计而非事后补丁；
- 禁止用户可见质量档位（既有产品纪律）：码率标定是内部自动决策。

### 3.6 竞品格局（先发窗口）

RealityScan=HEIC 静态（1.1 起，官方宣称缩 50%）；Polycam=静态照片+PNG 深度；
Scaniverse=双分辨率 JPEG；Luma=视频但云端处理。
**没有任何端上处理阵营的竞品在采集期写视频码流**——C 若做成是首创；
C-lite（HEIC 直切）则是"只抄已被证明有效的"最小步（RealityScan 出货验证）。

## 四、路线图（每步一个硬门，不过门不进下一步）

- **P0 探针（无产品改动）**：
  a) 真机 VTCompressionSession 探针：4224×2376 Level 6 硬编在机队最老档位（A14 起逐档），
     记录成败矩阵与兜底触发条件；
  b) E24 码率阶梯转码 + 全管线 parity 实验（3.4 节），产出"通过的最低码率"；
  c) 热 A/B：采集满负载 ± 硬编，进既有热压测 harness。
- **P1 C-lite（低风险先行）**：采集写 HEIC（intra 2×），归档端相应把 Lepton 层替换为 HEIC 字节直存；
  旧项目不受影响。全项目 1.5×，叠 B 后 2.9×。
- **P2 B 轨（需签决）**：修订冷归档合同（"可证明再生"替代"保存可再生模块"），
  实现种子+版本+抽查校验的再生通道，先拿 DB 199 MB 开刀。
- **P3 C 全量**：P0 三门全过后，采集写 HEVC GOP=8；按 parity 门通过的码率出货；
  Android 侧 MediaCodec 探测 + 硬件 H.264/JPEG 兜底。
- **反证条件**（任一成立即停该级）：最老档位硬编失败且兜底尺寸伤重建、parity 门在保守码率也不过、
  热 A/B 触发降频、GOP 随机访问税不可接受。

## 六、跨端实现架构（2026-08-04 追加，已实证）

用户约束：100% 跨端、不用 Swift、用 Dart。可满足，关键事实：**VideoToolbox 是纯 C API**（非 Swift），
**AMediaCodec NDK 也是纯 C API**——Dart FFI 两端直达。

- **Dart 拥有一切逻辑**：归档格式、GOP 索引、manifest、校验、随机访问、码率决策。双端逐字节同一实现。
- **Apple 平台层**：`pw_hevc/native/pw_vt_encoder.c`（~200 行纯 C，iOS/macOS 共用——回调→同步的信号量适配，
  这是 Dart NativeCallable 生命周期约束下的必要垫层）。零 Swift、零 Objective-C。
- **Android 平台层**：AMediaCodec 是同步拉取式 C API，Dart FFI 直接绑定，连 shim 都不用。
  兜底纪律不变：硬件 H.264 或保留 JPEG，绝不软编 HEVC（专利红线）。
- **跨端解码保证是规范级的**：HEVC 解码按标准位精确，同一码流在任何合规解码器输出相同像素。
  归档"到处可解、到处可校验"不依赖工程运气。
- **实证**（results/dart-ffi-equivalence.json）：同 96 帧同参数，Dart FFI 路径 21,312,594 B vs
  ffmpeg 路径 21,313,102 B（差值=容器开销），解码 96/96 帧，Y-PSNR 逐位小数一致（39.03/36.62 dB）。
  Mac 上验证的这份 C 文件与 Dart 代码就是将来编进 Flutter app 的同一份——开发在 Mac、测试在手机的
  工作流对这条管线完全成立。
