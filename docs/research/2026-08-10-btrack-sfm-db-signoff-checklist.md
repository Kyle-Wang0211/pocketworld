# B 轨签决清单：SfM DB（official_sfm_live.db）的去留

> 日期：2026-08-10。P2 去 JPEG 化上生产后，DB 成为盘占绝对大头，本文供签决。
> 事实全部来自仓库代码/实验记录，出处内联；未验证的假设明确标注。

## 〇、为什么现在到了签决点

P2 之后一个 150 张作品的构成（真机口径）：

| 项 | 现状体积 | 占比 |
|---|---:|---:|
| 照片（PWVA 码流接管后） | ~13 MB | ~8% |
| **SfM DB（ZPAQ 归档后）** | **~125–165 MB** | **~90%** |
| 稀疏 PLY + JSONs | ~几 MB | ~2% |

DB 已有生产归档线（ZPAQ 7.15 method5，双候选竞争+逐字节验证后删源，
`database_archive_transaction.dart`），但只有 **1.56–1.60×**——页级手段已证到顶
（VACUUM/索引重排无肉，exact_transform_v2 反向失败）。再往下只有一条路：
**不存字节，存再生配方**。这触碰冷归档合同"不删可再生模块"条款 → 需签决。

## 一、DB 里是什么、谁还在用它

**内容**（COLMAP schema，冻结样本 198,983,680 B 实测拆分）：

| 表 | 占比 | 性质 |
|---|---:|---|
| descriptors（SIFT 描述子） | **80.5%** | 匹配期的中间物；建图(mapper)不读 |
| keypoints | 15.1% | 建图需要 |
| matches + two_view_geometries | 3.6% | 建图需要 |

**PLY 落盘后仍读 DB 的路径只有一族**："重新重建点云"（me_page.dart:744-770
长按菜单，PLY 已存在时也提供；走 resume → native RunIncremental 直接从 DB 读
keypoints/matches，不需要任何照片帧）。导出/上传/渲染/取色一律不读 DB。

## 二、⚠️ 一个必须先说破的结构性事实

**P2 之后，DB 的"位级再生"已经死亡，不是工程问题，是物理问题。**

live DB 是拍摄期从**原版 JPEG 像素**上提特征建出来的。P2 已删除 JPEG 原件，
主本是 HEVC 码流——解码像素规范级确定、永远稳定，但**不等于**当初喂给提取器
的那份像素。同一套代码在解码帧上重跑，产出的是"同一场景的等价 DB"，
不可能逐字节复原旧 DB。

所以 B 轨对 DB 只有**语义档**：验收标准不是"字节相同"，而是
"从再生 DB 重建出的稀疏点云与原版过同一道 PLY 门"。
（这个门今天已经过过一次：PLY 门本身就是"解码帧全管线重跑"的实测，
96/96 配准、误差反低 0.003px、点数 +6.3%。）

## 三、证据现状盘点（诚实账）

| 证据 | 状态 |
|---|---|
| 派生 JSON/PLY 再生：规范形下 13/13 位级一致 | ✅ 已实测（btrack-mac-recon.json） |
| 解码帧全管线重建质量 ≈ 原版 | ✅ 已实测（PLY 门 PASS，Mac 口径） |
| **DB 再生本身** | ❌ **从未实测**（btrack-mac-recon 自陈"未测(重活)"） |
| GPU matcher "15/15 位级一致" | ⚠️ 只有口头转述，**仓库找不到结果文件** |
| 提取器（产出 80.5% 字节的那个）确定性 | ❌ 零记录 |
| mapper 不读 descriptors | ⚠️ COLMAP 通识+代码旁证，**未在本管线实测** |

## 四、方案（三选一，可先 B2 后 B1 分步走）

### 方案 A：维持现状（不签）
ZPAQ 线继续，~125–165 MB/作品。零风险零收益。

### 方案 B2：裁描述子（推荐先行）★
**原理**：作品完成（稀疏 PLY durably 落盘 + DB 归档验证过）后，descriptors 表
是纯中间物——"重新重建点云"只需要 keypoints+matches+TVG。把 descriptors 裁掉
再 ZPAQ。将来若真需要描述子（换参重匹配），从 PWVA 帧重提。
- **体积**：DB 200–260 MB → 裁后 ~39–51 MB → ZPAQ 后 **~25–35 MB**；
  作品总占 ~150 MB → **~45 MB**（DB 部分 ~5×，全作品再 3×）
- **不依赖**任何确定性证据（裁剪是删表不是再生）
- **保全**"重新重建点云"功能（前提=验证门 V1 过）
- 工程量：小（归档预处理链上加一个不可逆变换档 + manifest 记录 + 验证门）

### 方案 B1：全配方化（终态）
**原理**：DB 字节完全不存。存再生配方 manifest：PWVA 码流 SHA + 帧清单 +
提取/匹配参数 + 提取器二进制 SHA + git HEAD + seeds。需要 DB 时（用户点
"重新重建"）：物化帧 → 重提特征 → 重匹配 → 重建。
- **体积**：DB → ~0，作品总占 **~15 MB**（对 JPEG 时代约 40–50×）
- **前置**：①端上"离线重提+重匹配"harness（现在提取只在采集会话里活着，
  需要独立驱动器——中等工程量）；②确定性/质量证据补齐（见验收门）
- **税**：重新重建从"秒级开跑"变"先几分钟重提特征"（150 帧 GPU 提取+匹配，
  A16 实测口径拍摄期是跟拍实时的，离线批量预计 2–5 分钟）

### 推荐路径
**先签 B2**（收益 ~5×、风险最低、当月可上）；B1 等 B2 稳定运行 + 确定性
证据补齐后二次签决。两步互不锁死：B2 的裁剪 manifest 就是 B1 配方的子集。

## 五、风险清单（签字前请逐条过目）

1. **合同修订**：冷归档合同"不删可再生模块"→"可证明再生 + 抽查校验"。
   这是本次签决的实质。B2 删的是 descriptors 表（可从 PWVA 帧重提），
   B1 删的是整个 DB。
2. **位级→语义档降级**（见第二节）：P2 已使位级不可能，签 B 轨 = 接受
   "DB 是语义等价再生物"。稀疏 PLY 主本不受影响（它照旧原样存储）。
3. **"重新重建点云"功能**：B2 依赖"mapper 不读 descriptors"假设（验收门 V1
   实测把关，不过门不上线）；B1 该功能延迟变分钟级。
4. **未测依赖**：提取器确定性零记录、matcher 15/15 无落盘证据。B2 不依赖
   它们；B1 上线前必须补测并落盘（验收门 V4）。
5. **老数据**：只对新 capture 生效（创建期能力标记，与 Lepton/ZPAQ 同款
   纪律）；已归档的 .zpaq 一律不动。
6. **fail-safe 方向**：任何验证不过 = 保留现状字节（与 PWVA master 同款
   全有或全无），最坏结果是"没省到空间"，永远不是"丢了数据"。

## 六、验收门（不过门不上生产，全部留盘为证）

- **V1 功能门（B2 前置）**：真机上对一个已裁 descriptors 的 capture 走
  "重新重建点云"全流程 → 成功产出稀疏 PLY，与裁前重建结果过同 gauge
  PLY 对比（肉眼 + 配准/误差/点数指标带）。
- **V2 裁剪可逆性门（B2）**：裁剪产物 + PWVA 帧重提描述子 → 重匹配 →
  匹配拓扑与原 DB 对账（inlier 加权口径,允许语义差异带）。抽查校验协议:
  每 N 个作品随机抽 1 个做全量 V2。
- **V3 空间账门**：连续 3 个真实作品实测裁前/裁后/ZPAQ 后三级体积,
  达成 DB 部分 ≥4× 才算数。
- **V4 确定性门（B1 前置）**：同一 PWVA 码流重提+重匹配连跑 3 遍 →
  规范形（去墙钟/rowid）下逐字节一致；提取器二进制 SHA 与参数全部进
  manifest。不一致 → B1 永久降级为"语义档 + PLY 门抽查"。
- **V5 质量门（B1）**：再生 DB → RunIncremental → 稀疏 PLY,与原版 PLY
  过今天同款对比页（用户批准制）。
- **效率门**：裁剪/再生全部在冷归档协调器闸后跑（与 Lepton/PWVA master
  同调度）,拍摄期零新增工作——结构性免测,但装机后照常看一次遥测。
