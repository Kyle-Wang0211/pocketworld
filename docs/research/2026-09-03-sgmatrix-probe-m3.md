# 实测:M3 Pro 上 Dawn 暴露的子组矩阵配置(2026-09-03,主线亲测)

探针源码 `~/Developer/pw_matcher_speed_20260903/sgmatrix_probe.cc`(枚举全部 config,
非只查 f32;需 `allow_unsafe_apis` toggle 才能看见实验特性 —— 与生产 TU 同法,
pwofficial_gpu_match_dawn.cc:855-861)。本机 Dawn = aether_cpp 固定子模块。

```
adapter="Apple M3 Pro"  subgroup range=[32,32]
features: subgroups=1 subgroup-matrix=1 shader-f16=1 timestamp-query=1
subgroup matrix configs: 2
  cfg[0] in=f32 out=f32 M=8 N=8 K=8
  cfg[1] in=f16 out=f16 M=8 N=8 K=8
```

**判决**:Dawn 的 `SubgroupMatrixComponentType` 枚举**有** U8/I8/U32/I32/F16/F32
(webgpu_cpp.h:716-722),但 M3 的 Metal 后端**只填两条同进同出配置**:
- **没有 f16→f32 混合精度**(= Metal `simdgroup_matrix<half>`+f32 累加,原生 4.9ms 的根因);
- **没有 u8/i8→i32 整数 MMA**。

⇒ "用 WGSL 拿到 Metal 同款混合精度 MMA"这条路在本机 Dawn 上**不可得**(上游 tip-of-tree
是否已加、需要哪个 toggle,英文线在查)。**timestamp-query=1** 是好消息:分块成本模型
可以换成每缓冲 GPU 时间戳(之前只能用墙钟,是默认分块多花 2.5ms 的一半原因)。

## 由此得到的主攻方向:f16 两阶段精确法(算法路,不依赖硬件)

f16→f16 MMA **可用**,且 08-01 实测在老结构上 26.2→19.0ms(1.38×)。u8 点积和上限
128×255²=8,323,200 远超 f16 上限 65504 ⇒ 直算必溢出;**但可缩放**:u8/16 → 值域 [0,15.94],
逐积 ≤254,K=128 累加 ≤32,512,**在 f16 内不溢出**(累加结果 = 精确 dot/256)。
两阶段构造(可证逐字节等价):
1. 阶段一 f16 MMA 得近似 dot 与**误差界** ε(需推导:16 次 K=8 累加的 f16 舍入界);
2. 每行取"近似最大值 ± 2ε 覆盖到的候选集"(通常 1-3 个),**只对候选做精确整数重算**
   (每行几×128 MAC,相对 8192×128 可忽略);
3. 阶段二给出精确 dot ⇒ top-2 与 ratio 门与全精确路径**逐位相同**。
理论天花板:8192×8192×128 = 8.6 GMAC = 17.2 GFLOP;M3 Pro f32 峰值 ~7 TFLOPS ⇒
Metal 4.9ms ≈ 3.5 TFLOPS(50% 峰值),我们 11.0ms ≈ 1.6 TFLOPS(22%)。f16 通道翻倍
+ 候选重算开销 ⇒ 有望进入 5-6ms 区间,即**追平量级**。风险:f16 误差界若太松会让候选集
过大、阶段二吃掉收益;需实测。

## f16 MMA 的真实加速比(2026-09-03 22:0x,主线亲测,同夹具 ABBA)

台架 8192² 一对(db51 图 1-2,ratio 0.8),GPU p50:

| 核 | 结构 | GPU p50 | 匹配数 | 备注 |
|---|---|---|---|---|
| `mma` | 旧结构,f32 MMA | 25.38 / 25.12 | 984 | ABBA 双括号 |
| `mma16` | **同结构,f16 MMA** | **18.20 / 18.34** | **962** | **1.39×**(与 08-01 的 1.38× 独立复现);非精确(22 对差) |
| `fusedr128-db` | 前沿,f32 MMA + 融合 + 流水 | **11.67** | 984 | |
| Metal 原生 | — | **4.9** | 984 | 目标 |

**推论与下一刀**:
1. f16 通道在 Apple GPU 上只快 **1.39×**(不是理论 2×)⇒ 单靠 f16,db 结构预期 11.67/1.39 ≈ **8.4ms**,
   仍是 Metal 的 1.7×。**f16 是必要条件,不是充分条件。**
2. **f16 真正的复合价值:解开 32KiB 共享内存预算**。f32 下 Bsh 16KiB + accSh 16KiB 已顶满,
   正是 SR-3E 真双缓冲(需 2×Bsh=48KiB)与更大列 tile 死掉的原因。f16 让两者各减半 →
   **腾出 16KiB**:可选 (a) 列 tile 32→64(B 复用翻倍、barrier 减半),或 (b) 真双缓冲
   (2×8+8=24KiB 装得下)。之前被预算判死的结构刀在 f16 下全部复活。
3. 精确性由**两阶段**解决(f16 近似 + 误差界 → 仅对不可判定行精确重算),
   `mma16` 的 962 vs 984 正是需要被阶段二修正的量级(2.2%)。
4. 诚实边界:1.39 × (结构刀 ~1.3) ≈ 1.8× ⇒ 约 6.5ms,**追平 4.9 仍需额外机制**;
   "超越"目前没有已量到的路径。timestamp-query 可用 ⇒ 分块成本模型可换 GPU 时间戳
   (默认分块比单体多 2.5ms 的一半原因)。

## f16 两阶段的误差界推导(可证部分,写死备用)

- **输入精确**:u8 值 v∈[0,255],缩放 v/16 ∈[0,15.9375]。v 至多 8 位有效数字,除 16 是二的幂
  ⇒ v/16 在 f16(11 位有效数字)中**精确表示**,无输入误差。
- **逐积**:(a/16)(b/16)=ab/256 ≤ 254。ab 至多 16 位有效数字 > f16 的 11 位 ⇒ 乘积舍入,
  绝对误差 ≤ 254·2⁻¹¹ ≈ 0.124。
- **累加(关键,且规范未定)**:`subgroup_matrix_result<f16>` 的**内部累加精度规范未规定**。
  若硬件内部按 f16 累加,K=128 的和量级 ≤32512(f16 在 [16384,32768) 的间距为 16)⇒
  最坏 128 步 × 8 = 1024(/256 域)= 262144(精确 dot 域,占满量程 3%)—— **太松,不可用**。
  ⇒ **必须自己控制累加**:split-K —— 每条 MMA 只做 K=8(部分和 ≤2032,f16 间距 1),
  该块误差 ≤ 8×0.124(乘积)+ 8×0.5(累加)≈ 5(/256 域);16 个块的部分和在**寄存器里用
  f32 相加**(精确)⇒ 总界 **ε ≤ 16×5 = 80(/256 域)= 20480(dot 域,≈ 0.25% 满量程)**。
- **候选集充分性(逐字节等价的证明)**:设精确点积 d_i,近似 a_i 满足 |a_i−d_i| ≤ ε。
  取候选集 S = { i : a_i ≥ a_max − 2ε }(a_max = max a_i)。对真正的最优 j:
  a_j ≥ d_j − ε ≥ max_i d_i − ε ≥ (a_max − ε) − ε = a_max − 2ε ⇒ j ∈ S。同理次优 ∈ S。
  ⇒ **只要对 S 内候选做精确整数重算再取 top-2,结果与全精确路径逐位相同**(平局语义照旧:
  最小下标、升序严格 >)。
- **工程形态**:阶段一 f16 MMA 跟踪固定 K 个近似候选(如 K=8)与 a_max;若第 K 个候选
  a_K < a_max − 2ε,则 S ⊆ 已跟踪集合,充分;否则该行标记**回退全精确**(退化场景,应极少)。
  阶段二每行 ≤K×128 次整数 MAC,相对 8192×128 可忽略。
- 风险:ε=20480 若让 S 经常超过 K,阶段二/回退会吃掉 f16 的 1.39×。需实测 S 的分布。

## 判死 f16 路线 + 定罪 Metal 那 2.4× 的确切来源(2026-09-03 22:4x,主机数值实验)

真实 8192² 夹具(SIFT 描述子,L2 严格 = 512 ⇒ Cauchy-Schwarz 上限 dot ≤ 512² = 262,144,
**不是我先前算的 8,323,200** —— 那是无约束 u8 的上限):

| 量 | 值 |
|---|---|
| best 中位 | 253,809(= cos 0.968) |
| **best − second 中位** | **823**(占 best 的 0.32%);p1 = 7 |
| 保留行(过 ratio 门)的 gap | 中位 4,443,p10 2,284,**min 805** |
| 拒绝行的 gap | 中位 613,p90 2,275 |

⇒ **判决需要的分辨率是几百 / 254,000 ≈ 0.03% 相对精度。**

### 1. f16 两阶段(候选集回退)判死 —— 候选集就是整行
按推导 ε = 20,480 取候选集,实测 |S| 中位 **7,852 / 8,192**(K=2/4/8/16/32 全部 0% 覆盖,
8192 行全需回退)。原因就是上面那张表:gap 只有 823,而 ε 比它大 25 倍。两阶段退化为全精确。

### 2. f16 MMA 做**精确**整数点积:结构上不可能(可证)
f16 能精确表示的整数上限 = 2048。逐项检查:
- `u8×u8 逐积 = 65,025` ⇒ 超出,舍入;`K=8 部分和 = 520,200` ⇒ 远超。**直接 f16 MMA 不精确**(实测 mma16 962 vs 984)。
- **半字节(nibble)拆分可精确**:nibble 逐积 ≤225、K=8 部分和 ≤1,800 < 2048 ⇒ f16 内精确,
  再把 16 个 K 块在 f32 里相加 ⇒ 精确。**但需 4 趟 MMA**(hi·hi / hi·lo / lo·hi / lo·lo),
  4 ÷ 1.39(f16 速率优势)= **比现役 f32 慢 2.9×**。
- 只拆一个操作数(2 趟):`a·b_hi ≤ 3,825`,K=8 和 ≤30,600 ⇒ 超出。不可行。
⇒ **在 WGSL 今天的能力下,f16 MMA 无法用于精确 u8 点积。f32 MMA 是唯一精确 MMA 路径。**

### 3. Metal 快 2.4× 的确切来源(定罪,非推测)
Metal 用 `simdgroup_matrix<half>` 输入 + **f32 累加**:u8 在 f16 中精确;逐积 ≤65,025(17 位)
与总和 ≤262,144(18 位)**都在 f32 的 24 位尾数内精确** ⇒ **Metal 既精确又拿到 f16 的 2× 速率**。
WGSL/Dawn 在 M3 上**只暴露 f32→f32 与 f16→f16**(本文件顶部实测),**没有 f16→f32**。
⇒ **那 2.4× 的差距 = 一个缺失的 WebGPU/Dawn 能力(f16 输入 + f32 累加的子组矩阵配置),
不是我们的核写得差。** 我们的 f32 MMA 已接近 f32 硬件上限(1.6 vs Metal 3.5 TFLOPS 有效,
比值 ≈ f16:f32 的理论 2×)。

### 4. 因此剩下的真实杠杆(仍在做:"能提一点是一点")
1. **上游能力**:f16→f32 subgroup-matrix config —— 查 gpuweb/Dawn 有无进行中的提案/CL,
   有则跟踪(拿到就直接追平);
2. **开销层**(不动核):A 表常驻(prep 实测 ~1.1ms/对墙钟;一帧 K12 共享同一 query 表可只传一次)、
   分块策略(**未判**,需安静窗镜像 ABBA 重测);
3. **Vulkan 侧(安卓/鸿蒙)**:`dot4U8Packed` 在 Vulkan lower 为原生 `OpUDot`(Metal 上是软件
   polyfill)⇒ 非 MMA 的 tiled 路径在安卓可能是另一番景象,与 iOS 结论无关,需单独量;
4. 不再碰:f16 任何形态、空间布局族(tacc/s33/Direct-B)、真双缓冲(f32 预算下不可行)。

## 🎯 突破:混合精度不是硬件/标准缺失,是 Dawn 少登记了一条配置(已补,已验证)

追踪链(全部本地源码,可复核):
1. `dawn/src/dawn/native/metal/PhysicalDeviceMTL.mm:1038-1056` —— Metal 后端把配置表
   **硬编码成 2 条**(`new SubgroupMatrixConfig[2]`:f32→f32、f16→f16);
2. `dawn/src/dawn/native/ShaderModule.cpp:1728 ValidateSubgroupMatrixConfiguration` ——
   Dawn 拿 shader 的用法**逐条比对这张已登记表**,不在表里就在校验期拒绝;
3. `dawn/src/tint/lang/core/core.def:2858-2862` —— **WGSL 语言层早已声明混合重载**:
   `implicit(T: f16, TR: f32_f16, …) fn subgroupMatrixMultiplyAccumulate(left<T>, right<T>, result<TR>)`
   (另有 `T: iu8` 配 `TR: iu32` 的**精确整数** MMA 重载);
4. `dawn/src/tint/lang/msl/writer/raise/builtin_polyfill.cc:1194` —— MSL 生成端**类型无关**,
   直接把 `builtin->Result()->Type()` 转给 `simdgroup_multiply_accumulate`;
5. MSL 原生支持 `simdgroup_matrix<half>` 操作数 + `simdgroup_matrix<float>` 累加器 ——
   **我们自己出货的 Metal 核就是这么写的**(`pwofficial_gpu_match.mm` 的 aFrag/c/simdgroup_multiply_accumulate)。

⇒ 结论:**Apple 硬件支持、MSL 支持、WGSL 语言支持、tint 生成支持,唯独 Dawn 没登记。**

**已实施**:给 vendored Dawn 的 Metal 后端加第三条配置(`f16 in → f32 out, 8×8×8`,注释含出处),
重建主机 `libwebgpu_dawn.a`,探针复验:
```
subgroup matrix configs: 3
  cfg[0] in=f32 out=f32 M=8 N=8 K=8
  cfg[1] in=f16 out=f16 M=8 N=8 K=8
  cfg[2] in=f16 out=f32 M=8 N=8 K=8   ← 新增
```

**为什么它能同时给到"精确"和"速度"**:u8 ≤255 在 f16 中精确(11 位有效数字);逐积 ≤65,025(17 位)
与总和 ≤262,144(18 位)在 f32 的 24 位尾数内精确 ⇒ **点积逐位精确,无需任何缩放**;而输入侧
按 f16 走 ⇒ 拿到 Metal 同款的 half 输入速率,并且 **Bsh 与 A 的加载带宽同时减半**(16KiB→8KiB,
之前判死的更大 tile / 真双缓冲随之复活)。
