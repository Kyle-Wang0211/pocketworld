## P0-C 功能性：下架点了没用【调研·出处充分】

### 4. `admin_set_work_moderation` 不动 storage 对象
Supabase Smart CDN 官方原文："Revoking or expiring a token does not purge its CDN
cache entry"；缓存过的响应"can continue to be served for the same signed URL until
the CDN cache duration expires, even if the token in that URL has already expired"。
**唯一硬撤销 = 删除或改名对象**（"Deleting the object invalidates all cached entries
for that object across all tokens"，传播 ≤60 秒，不影响浏览器缓存）。

⇒ 迁私有桶 / 签名 URL **都不能**让下架变真。这也推翻了我在 migration 注释里写的
"残留风险仅限提前保存过 URL 的人"。
**必须在 RPC 里加删除/改名对象。工作量半天。**
出处：supabase.com/docs/guides/storage/cdn/smart-cdn

✅ **已完成（1da76c5）**：新建私有 quarantine 桶（无任何 RLS 策略 ⇒ 仅 service_role 可达），
下架时把全部五类资产**物理移出**公开桶。选 move 而非 delete 是为申诉可恢复
（DSA Art.17 / Santa Clara 都要求申诉路径）。**下架 fail-closed**：
任一资产未能移出就不翻数据库状态 —— 标记"已下架"而文件仍可下载会让审计日志撒谎。
⚠️ 端到端闭环待用户跑 verify_takedown.sh 实证。

### 5. 下载无大小上限【调研·出处充分 + 亲验代码】
`glb_cache.dart` 全量读进内存喂 native 解析器，滚到卡片即自动触发。

或 `dio.download()` 落盘 + `onReceiveProgress` 中断。

写死小数字会卡住未来的产品形态。⇒ **客户端守卫因此成为唯一防线**。

✅ **已完成（747c304）**：流式落盘 + 逐块计数 + CancelToken。
两条上限：下载 512MB（略高于桶上限，刻意不低于服务端接受值）、
内存 128MB（只约束必须物化成 Uint8List 的路径）。

🔑 用真实本地 HttpServer 跑了 4 个用例，**含"服务端不发 Content-Length 时仍被
逐块计数拦住"** —— 证明预检不是安全边界。

### 6. 签名 URL 的成本陷阱【调研·出处充分】
每个 token 是独立 cache key ⇒ 首次必 MISS；uncached egress $0.09/GB vs cached $0.03/GB。
若迁签名 URL 而不缓存 token 本身 ⇒ 3× egress 单价。
缓解：每 (path, 时间窗) 只签一次并存表复用。
**但鉴于 P0-C 的结论（签名 URL 不解决下架），迁移私有桶的优先级应下调**，
除非目标是"私密作品真的私密"（这是独立于下架的产品承诺）。

## P1 架构决策（需你签决，我不替你定）

### 7. 认证：退回 GoTrue vs 继续自建

**GoTrue 自带而自建流程全部丢失的**【调研·出处充分】：
邮件 2 封/小时、OTP 30/小时、**每用户 60 秒冷却**、`/verify` 360/小时 per-IP、
Dashboard 一键 CAPTCHA、内建枚举缓解。这些挂在 `/auth/v1/*` 中间件上，
Edge Function 根本不经过。

**自建的两个动因，逐一查证**：
- 动因 A「官方邮件模板不支持多语言」→ **可解**【亲验】：Send Email Hook 的 payload
  含完整 `user` 对象与 `user_metadata`，官方文档就有 internationalization 示例
  （`user.user_metadata.i18n`）。
- 动因 B「未确认账号占位阻塞重新注册」→ **不成立**【亲验】：Supabase 允许同邮箱
  再次 signUp 并重发确认信。

**但反方向的证据**【亲验】：官方流程有已知的"账号预劫持"问题——
未确认邮箱重复注册时**密码不覆盖**，仍是首次注册者设的
（supabase#29347、Discussion #14994）。攻击者先用你的邮箱注册并设密码，
你之后真注册并点确认，账号激活而密码是攻击者的。
**当前自建流程恰好规避了这个漏洞**（验证前不建 auth.users 行，每次整行覆盖）。

⇒ 这是真实的三选一，不是"官方一定更好"：
| 方案 | 得到 | 失去/风险 |
|---|---|---|
| A 退回 GoTrue + Send Email Hook | 官方全套防护、删掉 pending 表与明文密码、代码净减少 | 需评估预劫持暴露 |
| B 继续自建 + 补齐防护 | 规避预劫持、已做一半 | CAPTCHA/最小间隔冷却/枚举统一响应要自己补，且长期自背安全责任 |
| C 混合（注册走官方、重置自建 或反之） | 各取所长 | 两套流程并存的复杂度 |

**现在只有 1 个用户 = 做此决策的最低成本时机。**

## P2 凭据卫生（上线前该做，非阻塞）

### 8. 会话 token 明文存 SharedPreferences 【调研·源码级证据，已补齐】
落盘位置实证：`supabase_flutter` 默认 key = `sb-<项目ref>-auth-token`，
经 shared_preferences legacy API 加前缀 `flutter.` 存进 iOS `UserDefaults`，
**明文 JSON 含 refresh_token**。（我已在本地 pub-cache 核对 **2.12.4**
`lib/src/supabase.dart:117` 与调研分析的 2.17.2 实现一致。）

**方案**：自定义 `LocalStorage` 子类 → `flutter_secure_storage`
（**BSD-3-Clause**、11.0.0、2026-08-06 发布、verified publisher steenbakker.dev、
4474 likes、160/160 pub points、356 万次/30 天下载）。无实质替代品
（次名 `biometric_storage` 两年半未更新、下载量差 100×）。

**四个必须踩对的点**（踩错就是把用户登出）：
1. **key 必须是 `sb-<ref>-auth-token`**，*不是* 官方 README 示例里的
   `supabasePersistSessionKey` —— 后者在源码里被注释为
   "Only used for migration from Hive to SharedPreferences. Not actually in use."
   照抄示例做迁移会读不到老数据。
2. **accessibility 用 `first_unlock_this_device`**（= `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`）。
   Apple 官方：ThisDeviceOnly 类的项 "Aren't backed up" ⇒ 正好堵住"被未加密备份带走"
   这个威胁；而默认的 `unlocked` 会导致锁屏时后台刷新读不到 → 触发登出。
3. **迁移先写新、再删旧**（官方 main 分支注释原文：中断时宁可两处都有，不可两处都无）。
4. 迁移逻辑放进自定义 `LocalStorage.initialize()`，天然早于 `recoverSession()`。

⚠️ 已知风险：该包 10.0.0→10.1.0 曾出过"全体 iOS 用户被登出"的回归
（issue #1158）⇒ **锁版本 + 真机验证**。iOS 卸载重装 Keychain 残留是 iOS 行为、
官方不修（issue #897 closed/not_planned）。
✅ 我们只有 1 个用户，最坏成本 = 重登一次。

### ~~9. 重置密码后不吊销旧会话~~ 【已撤销 —— 这条我判断错了】
**该问题不存在。** GoTrue 自 2023-07-03（commit `b079c35`，最早 tag v2.79.0）起，
`admin.updateUserById(password)` 内部即执行 `Logout(tx, u.ID)`，
直接 `DELETE FROM sessions WHERE user_id = ?`，删除该用户全部 session。
commit 原文："When an admin changes a password for a user, the logout is also
performed now."；官方文档亦载："The user changes their password ... " 会终止 session。
代码路径上无 config 开关可关闭。
⇒ `password-reset-verify` **无需改动**。真实残留窗口 = 旧 access token 的剩余寿命
（默认 exp 1 小时，官方文档明载 "Access Tokens of revoked sessions remain valid
until their expiry time"），可在 Dashboard 调低 JWT expiry（官方不建议 <5min）。
⚠️ 顺带纠正：GoTrue **没有** `POST /admin/users/{id}/logout` 这个端点；
`admin.signOut()` 要的是该用户的**有效 JWT** 而非 userId，服务端拿不到，也不需要。
⚠️ Flutter 陷阱：Dart 的 `signOut()` 默认 scope 是 **local**（JS 是 global），
要全设备登出必须显式写 `scope: SignOutScope.global`。

### 11. 我自研限流器的三个缺陷【亲验·自查代码】
- **i. 冷却语义错误**（最实质）：只有 `window_start`+`hit_count`，无 `last_hit_at`
  ⇒ 实现的是"每窗口至多 N 次"而非"最小间隔"。第 14:59 发 3 封、15:01 再发 3 封全放行。
  （限额 3/15min 下最坏边界 6/15min，危害有限，但语义确实不是我以为的那个。）
- **h. fail-open**：RPC 出错即放行。理由不成立——RPC 失败时 pending 写入也会失败，
  保住的可用性是虚假的。应改 fail-closed。
- **g. key 用明文 email**：不必要的 PII 落库，应用 HMAC；且**缺项目级全局熔断**
  （攻击者打散邮箱即绕过 per-email + per-IP 两层）。
- ✅ e. 清理策略已有（pg_cron 每小时）。

## 3D 扫描隐私（重做完成，法条均取自一手原文）

### 法律定性：比想象的宽松，但有一条绝对红线

**GDPR — 对我们有利**。Recital 51 逐字："The processing of photographs should **not
systematically be considered to be processing of special categories of personal data**
as they are covered by the definition of biometric data **only when processed through a
specific technical means allowing the unique identification** of a natural person."
Art.9 禁止的是"biometric data **for the purpose of uniquely identifying**"。
⇒ 只要**不做人脸识别/比对/建模**，旁人偶然入镜**不是** Art.9 特殊类别数据，
不需要"明示同意"这个高门槛（但仍是普通个人数据，需合法性基础与删除权）。
⚠️ Art.2(2)(c) 的家庭活动豁免**保护用户不保护平台**——内容一旦公开发布，平台就是 controller。

**中国个保法 — 明显更严**（全国人大常委会公报 2021·6 原文）：
- 第二十八条把"生物识别"列为敏感个人信息，**没有** GDPR 那句"specific technical means"的限缩
- 第二十九条：处理敏感个人信息须取得**单独同意**
- 第二十六条：公共场所图像采集"应当为维护公共安全所必需…设置显著的提示标识"
  ——UGC 3D 扫描很难套进这个目的
- 第五十五条：处理敏感个人信息须**事前做影响评估**
⇒ 进一步支持已有的"中国区单独处理"定案。

**COPPA 2025 修订**（Federal Register 原文，2025-06-23 生效，**2026-04-22 合规期限已过**）：
16 CFR 312.2 第(10)项新增 "biometric identifier … such as … **facial templates**; or
**faceprints**"。⇒ 只要**不生成人脸特征向量**就不触发这一项。
⚠️ 真正的风险点是一直存在的第(8)项："A photograph, video, or audio file where such file
contains **a child's image or voice**" —— **缩略图 PNG 若含儿童影像直接命中**。
规避：条款明确 13+ 年龄门槛 + 不做儿童向设计（Polycam 就是这么做的）。

### 🔴 绝对红线（一步踩三部法）
**不要做任何人脸识别/比对/特征向量生成。** 一旦生成 facial template，
同时触发 GDPR Art.9 + 个保法第 28/29/55 条（单独同意 + 事前影响评估）+ COPPA 312.2(10)。
⚠️ 但**检测 ≠ 识别**：打码用的人脸检测只框位置、不比对身份，Art.9 的门槛是
"for the purpose of uniquely identifying"，打码的目的恰恰是防识别。
（⚠️ 未找到 EDPB 对此的专门指引，此为基于条文措辞的分析。）

### 技术风险：真正的短板是缩略图，不是点云
**CVPR 2019 实证攻击**（arXiv 1904.03303，Pittaluga 等）摘要逐字：
"such point clouds **retain enough information to reveal scene appearance and compromise
privacy**"，攻击输入是"point depth and **optionally color and SIFT descriptors**"。
⇒ 对我们的直接含义：
- 我们的交付点云**带颜色**（取色战役的产物）⇒ 比纯几何点云风险高
- 但**不含描述子**（B1"删描述子保匹配图"的副作用）⇒ 反演难度上升
- **缩略图 PNG 是真实图像，无需任何反演** ⇒ **任何打码措施应优先施加在缩略图上**
⚠️ 未找到针对"照片 SfM 稀疏点云中偶然入镜人脸是否可辨识"的直接研究，不做外推。

### 打码方案（若要做，许可证已逐个核实）
- 🏆 **iOS 首选：Apple Vision `VNDetectFaceRectanglesRequest`**（iOS 11+）——完全端上、
  零许可证、零模型体积、**不增加 privacy manifest 面**（Vision 不在 required-reason 五类里）
- 跨端次选：**`ORB-HD/deface`（MIT，1,554★）+ 内置 `centerface.onnx`**——
  代码 MIT、**权重也 MIT**（来自 Star-Clouds/CenterFace），两层都干净，
  且是 ONNX 可复用现有推理栈。⚠️ **deface 只做人脸，不做车牌**
- ❌ **Ultralytics YOLO 系 = AGPL-3.0**（已用 GitHub API 核实）——闭源商业 app 会被传染
- ❌ **OpenALPR = AGPL-3.0** ⇒ **车牌检测没有任何许可证干净的开源方案，这是真实空缺**
- ⚠️ **InsightFace 陷阱**：README 逐字"code … MIT"但"training data … **and the models
  trained with these data** … non-commercial research purposes only" ⇒ **代码可商用、权重不可**

### PrivacyInfo.xcprivacy 落地（常量取自 Apple 文档 JSON 端点）
required-reason 类别**只有 5 个**：FileTimestamp / SystemBootTime / DiskSpace /
ActiveKeyboards / UserDefaults。
- `C617.1` 原文覆盖的是"files inside the **app container**, app group container, or the
  app's CloudKit container"——而 app bundle 与 app container 在 Apple 术语里并非同一物，
  **未找到 Apple 明确说 bundle 算 container 的文档** ⇒ **改用构建期注入 Info.plist
  消掉该调用更干净**，不必在理由码之间赌
- `NSPrivacyTracking=false` + 空的 `NSPrivacyTrackingDomains` 两个都不能省
- 数据类型：`EmailAddress` + `OtherUserContent`（点云与缩略图）+ 视情况 `CrashData`；
  **源照片不上传 ⇒ 不要声明 `PhotosorVideos`**（声明了反而与实际不符）
- `EnvironmentScanning` 是判断题（Apple 定义指 ARKit 类 scene understanding，
  我们是照片 SfM，字面不完全吻合但语义相近）——倾向声明，但**必须与 App Store Connect
  的 App Privacy 问卷答案逐项一致**，否则不一致会被打回
- **`pw_hevc`（自研插件）必须自己加** —— Apple 原文："Your third-party SDK **can't rely
  on the privacy manifest files for apps** that link the third-party SDK"
- ⚠️ **不要整块复制网上现成的 manifest** —— Flutter 团队明确警告：manifest 是
  **对 Apple 的事实声明（attestation）**，抄错等于虚假陈述

### 隐私政策条款（Polycam 三段式，可直接抄结构）
1. 声明用途边界："not intended to be used to upload images containing identifiable individuals"
2. 把同意义务转移给上传者
3. **把告知义务也转移给上传者**："have provided a copy of this Privacy Notice to any
   individuals identified from those images"（让上传者成为 GDPR 意义上的告知执行方）
+ 社区准则加"未经明确许可不得发布含第三方个人信息的内容"
+ 13+ 年龄门槛 + 不知情收集则删除
+ **明写"源照片仅存本地、不上传、不进 feed"** —— 这是我们相对全行业的最大隐私优势，
  值得在隐私政策与 App Store 描述里讲出来
+ 若将来要用数据训练模型，必须像 Polycam 一样**明写**，否则事后无法回溯授权

### 🔴 与下架链路的致命耦合
隐私政策里的"应要求删除"承诺**依赖下架真的有效**。当前状态（已核实）：
七张卫星表已补齐、storage 读策略已改，**但 `admin_set_work_moderation` 仍不删除/改名
storage 对象** ⇒ 由于 works 桶是 public 且 CDN 缓存不因策略变更而失效，
**已缓存的 URL 仍可下载** ⇒ 删除承诺仍是空头支票。
**这是隐私合规与 App Store 1.2 共同的最高优先级前置项。**

## 首次提交的其余技术门槛（原调研 agent 挂死三次，以下由我自己查证）

### 加密出口声明 `ITSAppUsesNonExemptEncryption`
只用 HTTPS（URLSession/Supabase）+ Apple 系统加密 API（Keychain/CryptoKit/Security）
的 app **属于豁免**，应在 `Info.plist` 里写 `ITSAppUsesNonExemptEncryption = false`。
写进 plist 的好处：**避免每次上传都弹出口合规问卷**。不写会在 App Store Connect
留下 "Missing Compliance" 警告并阻断该构建进入审核。
⚠️ 我们还用了 Dart `crypto` 包做 SHA-256。哈希通常不被视为受管制的加密功能，
但**这一点我未找到 Apple 或 BIS 的原文确认**，若要绝对稳妥应咨询法务/走自我分类。

### 年龄分级新体系 —— 一个需要澄清的区分
新增 **13+/16+/18+**（原 12+/17+ 取消），要求在 **2026-01-31** 前完成新版问卷。
⚠️ **但那条截止日期针对的是"提交更新"**（官方措辞 "won't be able to submit app
updates"）。本项目**从未提交过、App Store Connect 里还没有 app record**，
所以不存在"错过截止已被阻断"的问题 —— 首次创建 app record 时会直接走新版问卷。
⇒ **这不是我早先担心的硬阻塞**，但答题时要按新体系走。
UGC app 建议档位：不进 Kids Category、metadata 不出现 "For Kids"，
并在条款里设 13+ 门槛（同时规避 COPPA）。

### App Review 需要 demo 账号（Guideline 2.1）
本 app 的社区内容需要登录才能完整体验 ⇒ **必须在 App Store Connect 的
App Review Information 里提供有效的测试账号与说明**，否则会以
"requires a login … without clear test instructions" 被判 2.1 不完整。
⚠️ 且**审核期间后端必须保持可用**（Supabase 项目不能暂停）。
建议：专门建一个审核用账号，预置几个已发布作品，让审核员一进去就能看到
feed / 举报入口 / 拉黑 / 删号入口。

IPv6-only 网络兼容性、iPad 兼容性要求（能否声明 iPhone-only 规避）、
