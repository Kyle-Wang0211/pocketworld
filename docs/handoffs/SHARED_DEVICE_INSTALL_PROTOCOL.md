## 三条规矩

### ① 生产机上永远不用 `flutter run` / `flutter install`

只用:

```bash
xcrun devicectl device install app --device <UDID> <包路径>
```

理由,按严重性:

- **`flutter install` 会先卸载** ⇒ 容器里**所有**采集会话一次性没掉。
  2026-08-18 已因此丢过 8 场。这是不可逆的。
- **`flutter run` 不抹数据,但整包覆盖** —— `Runner` + `App.framework` +
  所有 framework 全换成你这一棵树编出来的。
  2026-09-10 20:29 的 `Runner.app` build 138 就是这么装的,另一条线当天
  刚验完的 Swift 与 Dart 一次性回退到那棵树的状态,四条待验判据全部作废。

### ② 只换你改的那一个二进制(叠加,不是整包)

拿**机上现在那一版**当基线,只替换自己动过的那个:

| 你改了什么 | 换哪个 |
|---|---|
| Dart(`lib/**`) | `Frameworks/App.framework` |
| Swift / iOS 插件(`ios/Runner/**`) | `Runner` |
| C++ / WGSL / 管线 | `Frameworks/PWOfficialSfm.framework` |
| 渲染 | `Frameworks/thermion_dart.framework` |

这样对方的成果**逐字节保留**。extractor 线在 133/135/136 一直是这么做的
(实测:我的 132→他们的 133、我的 134→他们的 136,`Runner` 与 `App` 全 SAME),
所以两边的东西能一路共存;138 换成整包才一次性冲掉。

叠加之后**必须自证**:去签名比哈希,**只有你换的那个该 DIFF,其余全 SAME**。
有第二个 DIFF ⇒ 基线选错了,停下。

### ③ 包必须带名字:`Runner-<号>-<一句话标签>.app`

`Runner.app` 这个名字里没有身份 —— 装机闸只能**事后**从 `devicectl` 的 `url`
看出机上是谁的包。带名字之后,双方在**装之前**就能发现"机上不是我以为的那一版"。

### ④ 🔴 两条线改到**同一个二进制**时,不叠加 —— 从一棵树一起编

2026-09-10 当天就撞上了:extractor 线的 138(`completion-feedback`)改的是
`App.framework`,而 capture-ar 线的 139 也改 Dart。**同一个二进制,谁叠谁都会
把对方冲掉** —— 第 ② 条只在两条线碰**不同**二进制时成立。

判据(装之前就能发现,不必等事后取证):

> 组装时如果发现「**我要换的这个二进制,基线相对上一版也变过**」,
> 那就是同一二进制冲突,**停下,不要叠**。

正解只有一个:

1. 双方各自 `git commit` 到共享分支(**别停在未提交状态** —— 138 的改动当时
   是 `pw-extend-capture` 工作树里 11 个已改 + **4 个未跟踪**文件,而
   `git diff` **不含未跟踪文件**,差点漏掉两个模块和两份测试);
2. 由**后出包**的那一方在**一棵树**上 full build;
3. 自证:该二进制对**两边的基线**都 DIFF,其余仍全 SAME。

`pw_ship.sh assemble` 已加这道闸:它会拿基线和**上一版**比,发现你要换的那个
二进制在基线里也变过就告警。**让机器发现,不要靠人事后取证。**

## 完整流程

```bash
S=~/Developer/pw_backups/pw102_20260906/pw_ship.sh

# 1. 取号(被占则拒绝)
$S claim 139 my-change capture-ar

# 2. 叠加组装:拿机上那一版当基线,只换一个二进制
$S assemble 139 my-change app  ~/Developer/pw-head-0827/build/ios/Release-iphoneos/App.framework

# 3. 闸 + 安装(一条命令跑完,闸与 install 之间只隔一两秒)
$S install ~/Developer/pw_builds_20260904/Runner-139-my-change.app <机上那一版的包名>
```

`install` 会依次跑:

| 闸 | 判据 | 为什么 |
|---|---|---|
| 闸0 | 机上包**身份**(`.app` 目录名)== 你以为的基线 | 比号会被撞号骗过(09-10 两次) |
| 闸B | **逐场比条数**,每一场都在备份里 | 铁律 3。残缺备份比没有备份更危险;09-08 教训:不能看目录在不在 |
| 闸③ | 最后一次采集/重建活动距今 > 300 s | 别打断正在跑的重建 |
| 闸① | 进程表 > 50 行 | **阳性对照** —— 进程表拿不到时 grep 也查不到 app,会假装"没在跑" |
| 闸② | app 不在跑;**在跑就由脚本自己关掉后台**(见下) | 紧贴 install,中间不插别的事 |

### 闸② 的关法(2026-09-11 用户令改:agent 自己关,不再找人划后台)

用户原话:"以后装机策略直接换成,agent 自己直接删掉手机 app 的后台,然后安装。"

原来的做法是「app 在跑 → 拒绝装机 → 让人去划掉后台 → 回一句 → 重跑一遍全部闸」。
每次装机多一个来回,而且闸与 install 之间那个窗口还可能被重新拉起(实测撞到过两次)。

现在 `install` 自己关:

```
闸③ 过(近 300 s 无采集/重建活动)   ← 🔴 安全前提,必须在前
闸① 进程表阳性对照(> 50 行)
闸② app 在跑 → devicectl device process terminate --pid <PID>
              → sleep 2 → 重读进程表(并重跑闸①阳性对照)
              → 还在就再关,最多 3 次;3 次都关不掉 = 它正忙 ⇒ 拒绝装机,报给人
install
```

**三条不许动的边界:**

1. **顺序就是安全前提**:必须先过闸③。绝不为了装机去中断一场正在进行的采集或
   重建 —— 那是 08-18 丢 8 场采集的那一类事故。闸③ 不过,连关都不许关。
2. **只用普通 terminate,不升级 SIGKILL**。空闲的 app 该关就关得掉;关不掉说明
   它正忙,那就停下报给人,不硬来。
3. **关的是进程,不是数据**:`process terminate` 不卸载、不清容器。铁律 1
   (永不 `flutter install` / `uninstall`)照旧。 探针读不到值时报的是「**探针失效**」而不是
「条件不满足」—— 读不到 ≠ 读到了别的。
