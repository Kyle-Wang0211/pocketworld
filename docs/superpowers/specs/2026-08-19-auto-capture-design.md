2026-08-19。用户诉求原话:**"现在的拍摄只有一次一次按快门,太麻烦了。我需要加一个功能,
开着视频,自动一秒排一张照片。"**

本文档是设计(spec),不是实现计划。实现计划另出。

## 2. 不做什么(明确排除)

- **不录视频、不从视频抽帧**(D3)。
- **不新开捕获路径**:自动拍只是"替用户按快门",调用现有 `_onShutterTap()`。
- **不加用户可见的质量滑杆/档位**(既有产品铁律)。
- **不改手动快门的任何行为**,包括它"无论多热、队列多深都立即可拍"这一条。
- **不做文字说教式引导**(既有设计原则:"不教用户")。

## 4. 架构

### 核心原则

**自动拍不新开捕获路径,它只是"替用户按快门"。**

判定通过后调用现有的 `_onShutterTap()`,走同一个 `ManualCaptureQueue.enqueue()`。
因此 300 张上限、in-flight 守卫、12MP 静照并落、sidecar 落盘、SfM 喂帧、策展
**全部自动继承**。若自动拍自建一条捕获路径,这些约束就得抄一遍,抄一遍就会漏一条。

### 组件

| 单元 | 职责 | 依赖 |
|---|---|---|
| `lib/official_capture/auto_capture_governor.dart` | **纯函数**。输入(当前 pose、基准帧 pose、场景中位深度、HFOV、队列深度、热态、已拍张数、已采集时长、tracking 状态),输出**拍 / 不拍 + 不拍的原因**。含全部阈值常量。 | 无(零 Flutter 依赖) |
| `lib/official_capture/auto_capture_controller.dart` | **有状态编排**。挂在现成 pose 流上(**20–60 Hz**,见 §5.4),维护 tick 计时与基准帧,决定 fire 就调快门入口回调。管模式启停。 | governor + 快门入口回调 |
| `lib/ui/official_capture/` 内的模式切换 UI | 自动 / 手动 两态切换 + 自动态指示器 | controller |

纯谓词 + 有状态编排分离,是仓里现成写法(`shutter_backpressure_gate.dart`、
`sfm_feed_queue.dart` 都是纯谓词 + host 断言工具)。沿用,不另创风格。

`ar_capture_page.dart` 已 4830 行,**判定逻辑与编排都不进这个文件**;它只负责接线
(加模式状态 + 把 controller 挂到已有 pose 订阅上)。

## 5. 判据与阈值

设:
- `R` = 场景中位深度(米),由 ARKit `rawFeaturePoints` 现算(preview/coverage 已在每帧
  消费该数据,不新增数据源)
- `C0, z0` = **基准帧**(上一张成功入队的帧)的相机中心与光轴方向
- `C1` = 当前帧相机中心
- `P = C0 + R·z0` = 基准帧视场中心在场景深度处的**虚拟目标点**

### 5.1 下限判据(移动够不够 —— 不够就不拍)

满足**任一**即算"动够了":

| 判据 | 定义 | 阈值 | 出处 |
|---|---|---|---|
| **A 视差角** | `θ = ∠(C0 − P, C1 − P)`,即两个相机中心在虚拟目标点 P 处张开的夹角 | **≥ 5°** | 直接引用 `capture_coverage_cloud.dart` 的 `parallaxMinDeg`。**同源同值,不新造常数**(2026-07-11 真机标定过) |
| **B 视线转角** | 光轴方向 `z0` 与当前光轴的夹角 | **≥ 10°** | ⚠️ **无外部依据,保守起点,必须真机标定** |

> **为什么下限用精确视差角而不是"移动了多少米"**:直着朝物体走 8.8 cm 会满足任何
> 距离阈值,但 `C0`、`C1`、`P` 近似共线 ⇒ 视差 ≈ 0 ⇒ 正是双墙成因。距离阈值会把这种
> 移动放过去,精确视差角不会。**这是本设计自查时改掉的一处真缺陷。**

> **为什么还需要判据 B**:纯旋转时相机中心不动,视差角恒为 0,判据 A 永不触发。
> 而原地转身扫房间是真实用法(Scaniverse 三趟法的上仰/下俯就是纯旋转),必须能拍到。

### 5.2 上限判据(移动太多 —— 立刻拍,别等 tick)

把虚拟目标点 `P` 投影到**当前帧**图像平面,取它在两个轴上**各自**的归一化偏移:

```
sx = |u(P) - cx| / imageWidth
sy = |v(P) - cy| / imageHeight
```

再按**面积重叠损失**合成:

```
s = sx + sy - sx*sy          ( = 1 - (1-sx)(1-sy) )
```

`s >= 0.30` 即与基准帧的**面积**重叠 <= 70%,**立刻拍**。
(P 落到画面外或跑到相机背后时 s 视为 +inf,同样立刻拍。)

> **为什么是面积口径,而不是取两轴较大者**〔2026-08-19 评审改正〕:
> 两轴的重叠损失是**相乘**的 —— 面积重叠 = (1-sx)(1-sy)。取 `max(sx, sy)`
> 只看更差的那一轴,把另一轴的损失整个丢掉,于是斜向运动被系统性**低估**、
> R2 被系统性**推迟**:45 度斜向要到真实面积重叠掉到 **49%** 才触发,
> 比 RealityScan 官方下限 60% 还低,正是 RS 警告的「断裂成不相连的组件」那一档。
> 而「绕物平移的同时抬高/压低手机」(Scaniverse 三趟法的上仰/下俯)正是这种轨迹。
> 面积口径在纯横移时退化成 `sx`、纯纵移时退化成 `sy`,§5.3 的标定数字逐位不变。
>
> 早期草稿写的是 `s = |proj(P) - 画面中心| / 画面宽度`(二维偏移的模、且两轴
> 都除画面宽)—— 纵向该除 `imageHeight` 才对,该式已作废。

> **已知盲区:纯 roll(绕光轴自转)不触发本判据。**
> 相机中心不动、光轴方向不变、目标仍在画面正中,于是视差角、视线转角、中心偏移
> 三者同时为 0,三道判据一致判「没动」。
> 这是**有意的**:纯 roll 既不改变相机位置也不改变视线方向,对重建**不提供
> 任何新的视点信息**,画面只是在图像平面内转了个角度。
> 所以本判据涵盖的是**平移 + pitch/yaw 及其任意组合**,**不含 roll** ——
> 早先「一个式子涵盖平移、旋转及其组合」的说法是超售,已改正。

`fx / fy / cx / cy` 与 `imageWidth / imageHeight` 由 ARKit 相机内参现算,
**不写死、不猜**。

⚠️ 两者必须来自**同一坐标帧**:native 侧 `intrinsicArr` 取自
`frame.camera.intrinsics`、`imgW/imgH` 取自
`CVPixelBufferGetWidth/Height(frame.capturedImage)`,都是原生相机图口径(横向),
契约成立;调用方**不得**把预览/显示(竖向)尺寸传进来,否则 sx/sy 会整体错一个
宽高比。〔2026-08-19 评审提出、控制器核实 native 侧后确认契约成立〕

### 5.4 ⚠️ pose 流不是 6 Hz,特征点是 8 Hz(2026-08-19 T3 评审核实,原文写错)

早先本文档与计划多处写「6 Hz pose 流」——**这是错的**,我把画质块的节流频率
当成了 pose 的频率。逐条核实 `ios/Runner/OfficialAetherARKitPlugin.swift`:

| 量 | 真实值 | 出处 |
|---|---|---|
| **pose 事件** | **逐 ARFrame,20–60 Hz** | `sessionDelegate.onFrame = { broadcast(frame:) }`(:779),**无节流**;注释原文「ARFrames (~17-50 ms)」(:642) |
| 画质块(gray128) | 6 Hz | `qualityInterval = 1.0/6.0`(:617) ← **6 Hz 出自这里,与 pose 无关** |
| **特征点 previewPoints** | **8 Hz** | `previewPointInterval = 1.0/8.0`(:624),在 :2685 独立判定后才并进 payload |

**推论:30 fps 时约 3/4 的 pose 帧不带特征点。**

这直接影响基准帧:`medianSceneDepthM` 吃的是**当前帧**的 previewPoints,
拿不到就 `depthTrusted=false`。而基准帧在 `start()` 与**每次成功入队**时重算 ——
两者都有约 3/4 的概率落在不带特征点的帧上。

配合 §7 的重播种规则,功能不会死锁,但会有一个**系统性偏置**:
基准帧被推迟到"入队后第一个带特征点的帧"才落定,最多晚 125 ms。
按 1 m/s 步行 = **12.5 cm**,与 §5.3 的平移下限(1 m 物距处 8.8 cm)同量级
—— 是偏置,不是噪声。

⇒ 控制器须记住**最近一次可信深度**:当前帧拿不到特征点时沿用它并保持
`depthTrusted=true`(场景深度在 125 ms 内不会突变,这比退回写死的兜底深度诚实),
使基准帧能锚在**真正入队的那一帧**上。

### 5.3 阈值汇总

| 量 | 取值 | 出处 |
|---|---|---|
| 视差下限 | **5°** | `parallaxMinDeg`,同源同值 |
| 视线转角下限 | **10°** | ⚠️ 无外部依据,待标定 |
| 重叠上限 | **归一化偏移 `s` ≥ 0.30**(即重叠 ≤70%) | D6;KIRI 官方 70%、Polycam 70–75%、RS >60% |
| tick 间隔 | normal 1.0s / soft 2.0s / hard 3.0s | 复用现成 `ShutterPace`(`shutter_backpressure_gate.dart`) |
| 张数上限 | **300** | 既有 `kOfficialMaximumCaptureFrames`(2026-07-27 已签) |
| 时间上限 | **5 分钟**(已签决) | 两条独立吻合:Scaniverse 官方硬上限 5 分钟;1 张/秒 × 300 张 = 5 分钟 |

参考数量级(HFOV=60°,仅示意,运行时按实测内参算):

| 物距 R | 侧向平移达到视差 5° | 侧向平移达到 `s`=0.30 |
|---|---|---|
| 1 m | 8.8 cm | 34.6 cm |
| 3 m | 26 cm | 104 cm |

窗口约 4 倍宽,两门不打架。

> 早期草稿曾写死 `[5cm, 50cm]` 钳位并分开定 `d_max` / `φ_max` —— **均已删除**,
> 现在下限是精确视差角、上限是统一重叠判据,两端都有出处。

## 6. 触发规则

```
R1(每 tick,间隔由 ShutterPace 决定):
    now - lastTickAt >= interval
    AND (视差角 >= 5°  OR  视线转角 >= 10°)      ← §5.1 下限
    -> fire

R2(每个 pose 事件,**20–60 Hz**,不等 tick):
    s >= 0.30                                     ← §5.2 上限
    -> 立刻 fire
```

R2 治的是"用户走得快,1 秒已经跨过重叠下限"——
这种情况按 1s 节奏拍会拍出 RS 官方警告的那种断裂组件。

### ⚠️ 由此产生的行为,与用户原话不同,须知悉

**"一秒一张"是节奏的下限,不是上限。** R2 生效时,快速移动可能 0.3 秒就拍一张。
这与用户字面要求("自动一秒排一张")不完全一致,但方向正确(保重叠),
且正好让我们与三家同行的连续运动判定对齐。

### 判定输出

```
enum AutoCaptureDecision {
  fire,
  skipNotMoved,     // 视差与转角都不够(§5.1 两条都不满足)
  skipPaced,        // 队列深,间隔已拉长,本 tick 未到
  skipTracking,     // tracking 非 normal
  skipCapped,       // 到 300 张
  skipTimeLimit,    // 到时间上限
}
```

### 基准帧更新规则(易错点)

**只有入队成功才更新基准帧**(`C0, z0` 与深度 `R` 一并更新)。
入队失败(队列不收 / 到上限)时基准帧不动 —— 否则下一 tick 会拿一个根本没拍成的
位置当基准,位移闸直接漏判。

## 7. 边界行为

| 情况 | 行为 | 理由 |
|---|---|---|
| 自动 → 手动模式 | 自动拍立即停;**已拍帧全保留**;队列继续消化 | 切模式是 UI 行为,不该动数据 |
| 手动 → 自动模式 | **不自动开始**,需用户点「开始」 | 避免进页面还没对好景就已在落帧 |
| 到 300 张 | 自动停止自动模式 | 快门入口本就硬卡死;提前停是为了不每秒撞一次墙 |
| 到时间上限 | 同上 | D8 |
| tracking 丢失 / limited | 暂停触发,**且基准帧不更新** | 丢失期间位置估计不可信,拿它当基准会让恢复后第一张判错 |
| App 退后台 | **停止**自动模式(不是暂停) | 回来时 AR 世界原点可能已重定位,继续拍会产生坐标系错乱的帧。复用现有 `cancelPending()` / `freezeAndDrain()` |
| 热态 critical | 只拉长间隔,**不停止** | 既有铁律:热是正常工况,停止 = 把热当借口 |
| 入队失败 | 基准帧不更新 + 记遥测 + 下 tick 重试 | 同 tracking 那条 |
| 拿不到场景深度(特征点太少) | 退化为**只用转角触发**,平移阈值锁保守下限 | 不能因为拿不到深度就罢工 |
| **基准帧不可信、而当前帧可信** | **立刻用当前帧重播种基准**,该帧只重播种不判定 | 见下方「⚠️ 死锁」—— 不补这条,上一行的降级会变成永久的 |
| **拿不到相机内参 / 画幅** | 上限判据返回 **null**(不是 +inf),只用下限判据决定 | 内参非法时若返回 +inf,R2 会把它读成「立刻拍」 —— 等于把「不知道」编码成「马上开火」。〔2026-08-19 评审补〕 |

---

### ⚠️ 死锁:降级必须可逆(2026-08-19 T3 评审实测复现)

`depthTrusted` 是在**播种基准帧那一刻锁死**的,而它**同时关掉两条路**:
视差判据(下限)与重叠判据(上限)都查**基准帧**的这个标志,不是当前帧的。
基准帧此前只在 `start()` 与**成功开火之后**重播种。

于是有这样一条路径:

1. 用户对着白墙 / 地板 / 无纹理面点「开始」⇒ 特征点 < 8 ⇒ 基准帧 `depthTrusted=false`
2. 视差路与上限路**双双失效**,只剩视线转角
3. 用户横移绕物、镜头朝向基本不变 ⇒ 转角恒 ≈ 0 ⇒ **永不开火**
4. 不开火就**永不重播种** ⇒ 回到第 2 步

**实测**(控制器复现,单变量,唯一差异是 `start()` 那一帧的特征点数,其后 180 帧完全相同):

| 起跑帧 | 30 秒横移的产出 |
|---|---|
| 特征点充足 | **30 张** |
| 特征点不足 | **0 张** |

不是"少拍几张",是**一张都没有,而且永远不会有**。无纹理面在室内采集里不是边角料,
是常态 —— 这条降级原本写的是"临时退化",实际是**永久锁死**。

⇒ 故加上表中那一行:**基准不可信而当前帧可信时,立刻重播种**。降级必须是可逆的。

## 8. UI 反馈(必需项,非锦上添花)

### 8.1 形态:按 RealityScan 截图 100% 复刻(2026-08-19 用户提供实机截图)

底栏一排(从左到右),与现有 `_ManualCaptureBar` 的结构逐格对应:

```
[相册缩略图+进度环]   [模式 toggle]   [快门]   [完成箭头 →]
                      ↑ 新增          ↑ 变色
```

| 元素 | 手动模式 | 自动模式 |
|---|---|---|
| **模式 toggle**(快门**左侧**) | 灰底,摄像机图标 | **蓝底**,摄像机图标 |
| **快门** | **白色**圆(现状不变) | **红色**圆(录制键) |
| 快门上方提示行 | 「Keep taking pictures to capture.」的中文等价 | 「Tap the record button once to start capturing.」的中文等价;**开拍后**换成停止语义 |
| 顶部说明条(**瞬态**,见下) | 「绕物成圈拍摄,覆盖所有角度,相邻照片挨紧」 | 「对着物体从各个角度看过去,它会自动拍」 |
| 切换瞬间 | — | 居中浮出一条 **「自动拍摄已开启」** 的短提示(RS 的 "Auto Capture On") |
| `N/300` 计数 | 沿用现有 `_AlbumCountFraction`,两模式相同 | 同左 |

**默认进入自动模式**(D9)。但**不自动开拍** —— 与 §7「手动 → 自动:不自动开始」一致,
也与 RS 截图上的 "Tap the record button once to start capturing" 一致。
净效果:用户从「点 300 次」变成「**点 1 次**」,而「什么时候开始」的控制权不变。

#### 顶部说明条必须是瞬态的(2026-08-19 用户裁定)

**只在进采集页与切模式时出现,3 秒后自消**(复用页面里 `_HardRejectToast` 同款的
3 秒时长,不新造常数)。**不常驻。**

理由 —— 这条原本会同时撞上三样东西:

1. **2026-07-27 已签决定**:开拍即弹的入场提示已被删除,原话是「每次进拍摄都
   **挡一次取景框**、说的又是用户还没到的事」;而且那次明确把四条瞬态横幅
   (硬拒/移速/starved/未连接)**放回各自的固定档位,不再为入场提示让位偏移**。
   常驻方案等于把那个偏移(+44)又加回来,是在推翻一条签过的决定。
2. **产品铁律「不教用户」**。
3. **本文档 §8 自己**写的「不上文字说教,只用指示器状态说话」。

⇒ 瞬态方案三样全不冲突:RS 的卡片样式、文案、位置一字不改,新用户照样看得到引导,
老用户不被永久挡取景框;四条瞬态横幅**保持原档位,不得整体下移**。

一句诚实的说明:RS 那条提示到底是不是常驻,从静态截图判不出来。这里选瞬态,
是因为它在**我们**的约束下是唯一不推翻既有签决的形态,不是因为查实了 RS 也这么做。

⚠️ 自动模式下**没有**独立的手动快门:那颗红色圆就是开始/停止键(RS 同款)。
需要手动补拍就切回手动模式。



位移闸意味着用户站着不动时**一张都不拍**,屏幕上显示"自动中"而张数不涨 ——
不给反馈用户一定以为坏了。

按既有"不教用户"原则,**不上常驻的文字说教**,只用指示器状态说话
(§8.1 的顶部说明条是**瞬态**的一次性引导,不属于此处所禁的常驻说教):

- 落帧时 → 指示器脉冲一次
- 位移不够 → 指示器转暗 / 静止(表达"在等你动")
- 队列拉长节奏 → 指示器节奏自然变慢(不额外解释)
- 张数 → 沿用现成的 `N/300` 分子分母口径

## 9. 与同行的已知差异(自审结论)

### ✅ 四家印证、未走偏

运动触发范式(RS/Polycam/KIRI 三家 auto 全是 motion-based)、70% 重叠
(KIRI 逐字 70%、Polycam 70–75%、RS >60%)、20 张起(四家一致)、
模式切换形态(KIRI 就是三模式切换)、转角也触发
(KIRI 用陀螺仪;Scaniverse 三趟法的上仰/下俯本身就是旋转帧)。

### ⚠️ 差异 1:视差下限是我们独有的

四家官方文档**没有一家**提到"移动太少就别拍",他们只讲重叠(上限侧)。
我们有,是因为自己的 coverage cloud 把低视差判成双墙成因,且 5° 已真机标定。

**这不是相违背**(更严格,只会少拍冗余,不会漏掉有效帧)。但存在一个诚实的疑问:
**同行不设下限,可能是因为手持绕物时下限根本很少触发** —— 若如此,这道门无害但也无用。
文档判不了,**必须真机实测"下限触发率"**(见 §11)。

### ✅ 差异 2:命名冲突 —— 已解决

KIRI 与 Polycam 的"Video 模式"是**真的录视频并从视频建模**;我们不存视频(D3)。
若沿用"录像模式"之名,用过那两家的用户会以为在录视频、会找视频文件。
**故改名为「自动 / 手动」**(D2),与 KIRI 的 Manual/Auto 叫法一致,语义与实现完全对应。

### ✅ 差异 3:时间维度 —— 已解决

Scaniverse 官方有 5 分钟硬上限,我们此前只有 300 张。自动拍会让 300 张变得容易撞到
(手动很少有人按 300 次),而热与 tracking 漂移会一路累积;Scaniverse 官方明说
"短而覆盖好 > 长而有空洞"。**故加时间上限**(D8)。

### 📝 差异 4:结构化引导(不在本次范围)

Scaniverse 的三趟法(平视/上仰/下俯)与顺逆时针两趟比我们的引导更结构化。
不冲突,仅记录,不在本次范围。

## 10. 测试

### ① host 纯函数测试

沿用仓里现成做法(`tool/sfm_feed_queue_check.dart`:纯谓词 + 合成输入 + 断言)。
喂合成 pose 轨迹,断言:

1. 原地静止 60s → **零触发**
2. 匀速绕行 → 触发间隔稳定,且相邻帧视差 ≥5°、`s` <0.30(重叠 ≥70%)
3. 快速平移 → R2 提前触发生效,相邻帧 `s` **不越过 0.30**
4. **纯前进**(沿光轴朝物体走)→ **零触发**(视差恒 ≈0,距离阈值会误放行,精确视差角不会)
5. 纯旋转 → 按视线转角触发(视差恒 0,只能靠判据 B)
6. 队列深 → 间隔拉长(1s→2s→3s)
7. 第 300 张 → 停止,不再触发
8. 到时间上限 → 停止
9. tracking limited 期间 → 零触发**且基准帧不动**
10. 入队失败 → 基准帧不动,下 tick 重试

### ② 真机实测(不可省)

单测证明不了这功能能用。既有教训"装机≠生效"与"静默 bug 只能靠金标准逐层对拍"
都指向这一层。

- `add_frame` 单帧耗时打点 —— **唯一还缺的关键数**,决定积压曲线
- 一次完整绕物采集:实际张数、相邻帧视差分布、拍完到 finalize 的等待时长、热曲线
- **单变量对照**:同一物体、同一路径,手动一次 / 自动一次,比点云

## 12. 已知成本(不粉饰)

`sfm_feed_queue.dart` 的架构保证(07-12 签决的三角约束:快门不限流 / 队列不丢帧 /
不降质)意味着 **1 张/秒不会 OOM、不会丢帧** —— 溢写磁盘排队,内存与队列深度无关。

**代价被挪到了别处**:finalize 要等队列彻底排空,所以**积压会变成"拍完之后的等待"**,
顶着既定的"拍完 ≤30s"预算。D7 的自适应节奏就是为了压住这条,但压不压得住
取决于 `add_frame` 单帧耗时 —— 那个数现在还没有。
