# 双拍摄管线完整复制设计

日期：2026-07-22  
状态：已由用户明确选定“整条管线完整复制”方案

## 目标

用户点击拍摄按钮后先选择“自研”或“官方”。第一阶段两条路线的行为和产物必须与当前自研路线一致，但“官方”路线必须是一套可独立修改的完整物理副本，不能是参数别名、策略分支、依赖注入配置或对现有自研管线的转调。

后续所有官方化工作只修改“官方”副本；现有“自研”路线保持为产品基线。

## 已选方案

采用完整双栈：除最外层入口选择器、通用设计令牌及操作系统/Flutter等平台依赖外，拍摄和重建链的应用代码、运行状态、通道、符号、缓存和产物全部分开。

明确拒绝以下两种方案：

1. 两个按钮调用同一个 `ARCapturePage` 或同一个 `SfmLiveRecon`。
2. 共享一套管线，仅通过 `enum`、配置文件或环境变量切换算法。

## 用户交互

1. 用户点击当前“+”拍摄按钮。
2. 弹出与产品视觉一致的半透明选择面板，两个等权入口：
   - 自研：当前产品基线。
   - 官方：官方对齐路线；第一阶段内部仍是自研实现的完整副本。
3. 选择后进入对应的独立拍摄页面。
4. 拍摄页面保留一个低干扰路线标记，避免两个初始外观相同时用户混淆。
5. 两条路线的作品都进入同一个“我的作品”列表，卡片明确显示“自研”或“官方”标签。

## 完整复制边界

| 层 | 自研基线 | 官方副本 |
|---|---|---|
| Flutter拍摄页 | 当前 `ARCapturePage` | 独立 `OfficialARCapturePage` |
| Flutter拍摄会话 | 当前 `CaptureSession` 及其 provider | 独立官方副本 |
| Dart AR通道 | `aether_arkit` / `aether_arkit/pose_stream` | 唯一的官方 MethodChannel/EventChannel 名称 |
| iOS插件 | `AetherARKitPlugin` | 独立 `OfficialARKitPlugin` |
| iOS平台预览 | `aether_arkit_preview` | 独立官方 platform-view id 与 factory/view |
| Dart重建调度 | 当前 `SfmLiveRecon` | 独立官方副本、worker协议和消息类型 |
| Dart FFI | 当前 `AetherSfm` / `pwsfm_*` | 独立官方 binding 与符号前缀 |
| Native适配/算法 | 当前自研实现 | 源码完整复制、独立编译目标及符号命名空间 |
| GPU提取/匹配 | 当前自研实现 | 独立源文件、Metal状态及导出符号 |
| 数据库/队列 | 当前DB与spool | 独立官方DB、spool和恢复标识 |
| 遥测 | 当前日志事件 | 路线字段和独立组件名，能够分组对比 |
| 最终产物 | 当前PLY/manifest | 独立官方产物路径和manifest身份 |

任何官方副本文件不得 import、调用或动态转发到自研管线的应用层实现。第三方系统框架可以共同依赖，但两套产品管线必须分别编译和持有自己的状态。

## iOS运行约束

两套Swift插件都在App启动时注册，但只有用户选中的插件允许启动 `ARSession`、相机和平台预览；未选路线保持未启动状态。离开页面时必须停止对应会话。这样既保持完整代码独立，又不让两条路线同时争抢iPhone相机。

Native侧不能把两份同名静态符号同时 force-load 进Runner。官方副本必须使用独立的C ABI前缀、编译目标和隐藏内部符号，链接门必须验证两套导出符号同时存在且互不解析到对方。

## 数据与作品列表

- 每次拍摄在创建时写入不可变的 `pipeline_kind`：`self` 或 `official`。
- 两条路线使用不同的捕获目录命名空间、数据库名、spool名、恢复键和产物名，防止续跑或清理误读另一条路线。
- `ScanRecord` 持久化路线字段；旧记录缺失该字段时按 `self` 迁移。
- “我的作品”继续聚合展示两类记录，卡片显示路线标签；排序、打开作品和社区能力保持原行为。

## 第一阶段行为约束

- 不修改任何重建参数、门槛、过滤、BA、特征或匹配算法。
- 官方副本初始配置和执行顺序必须与复制时的自研基线一致。
- 两条路线必须是不同类型、不同通道、不同FFI符号、不同native session和不同存储路径。
- 不以代码抽象或共享实现来减少复制量；当前任务的目的就是建立可独立演化的两份基线。

## 错误处理

- 用户取消选择面板时不进入任何拍摄页。
- 某一路线初始化失败时，只显示该路线的错误，不回退或偷偷调用另一条路线。
- 恢复任务必须按 `pipeline_kind` 回到原路线；不存在跨路线恢复。
- 发现通道、符号、数据库或目录碰撞时 fail closed，不自动合并。

## 验收

1. Widget测试证明“自研”和“官方”分别导航到不同页面类型。
2. 静态边界测试证明官方应用代码不导入自研拍摄/重建实现。
3. iOS测试证明两套MethodChannel、EventChannel和platform-view id全部唯一。
4. 链接/符号检查证明两套FFI ABI均存在，且官方binding只解析官方符号。
5. 存储测试证明两套目录、DB、spool、manifest和恢复任务互不碰撞。
6. 作品列表测试证明旧记录显示为“自研”，新记录按实际路线显示标签。
7. 配置快照测试证明复制完成时两套算法配置等价。
8. Flutter分析、单测、iOS Profile构建通过。
9. 真机分别进入两条路线，确认只有选中路线占用相机，两边均能拍摄并产生带正确标签的任务卡。

## 非目标

本阶段不把第二条路线改成官方COLMAP，也不调整任何算法。完成双栈复制并在真机验证后，才在“官方”副本上逐项替换和对齐官方实现。
