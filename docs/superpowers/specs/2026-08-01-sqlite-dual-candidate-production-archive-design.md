# SQLite 双候选生产归档设计

## 目标

未来官方项目完成后，针对 `official_sfm_live.db` 同时生成并验证两个候选：

1. `raw_v1`：原数据库直接使用固定的 ZPAQ 7.15 method 5；
2. `track_delta_v1`：临时副本先执行可逆轨迹描述子差分，再使用同一 ZPAQ。

只发布严格恢复为原数据库且体积最小的候选。事务完成后只保留一个归档，
原数据库最后删除。

## 数据与版本边界

- `raw_v1` 和 `track_delta_v1` 是清单中的显式预处理版本。
- 旧版 v1 清单按 `raw_v1` 读取，现有归档不迁移。
- `track_delta_v1` 不改变描述子数值、顺序、匹配、SQLite 页面或任何其他
  字节；逆变换后的完整 `.db` 必须与源文件 SHA-256 和逐字节一致。
- 不支持的 SQLite 布局、空轨迹、预处理错误或取消只淘汰轨迹候选，不能
  破坏原始候选或源数据库。

## 生产事务

1. 检查完成产物、归档策略、SQLite sidecar 和生产管线门禁。
2. 记录源数据库长度和 SHA-256。
3. 生成 `raw_v1` 临时归档，解压并验证完整源数据库。
4. 生成 track-delta 临时数据库和归档，解压、逆变换并执行相同验证。
5. 在所有通过验证且小于源文件的候选中选择最小者；相同大小优先
   `raw_v1`，减少不必要的格式复杂度。
6. 原子发布唯一归档及 v2 清单。清单记录预处理版本和两个候选的审计体积。
7. 再次检查生产门禁，最后删除源数据库和所有临时文件。

任何阶段取消、崩溃或失败都保留源数据库。已有“清单已提交但源仍存在”的
恢复路径按清单预处理版本完整复验后，才能补做最后删除。

## 恢复

恢复器先校验归档长度和 SHA-256，再用 ZPAQ 解压。`raw_v1` 直接验证；
`track_delta_v1` 先逆变换到第二个临时文件，再验证源长度和 SHA-256，最后
原子改名为 `official_sfm_live.db`。中间的变换态数据库永远不能暴露给训练
或重建管线。

## 中断与资源

预处理器与 ZPAQ 都支持协作取消。捕获、稀疏/稠密重建或其他生产活动开始
时，协调器同时取消二者；事务在安全边界退出并下次重跑。每个候选完成后尽早
删除不再需要的临时数据库，避免保留两个永久副本。

## 独立真机 bundle

使用独立入口和 bundle ID `com.kyle.PocketWorld.ArchiveBench`。测试数据库
只复制到该 bundle 的独立 Documents，绝不访问、安装或更新
`com.kyle.PocketWorld`。真机运行生产同一 Dart 事务、FFI 预处理器和 ZPAQ，
回传两个候选体积、选择结果、耗时、源/恢复 SHA-256、逐字节结果、
`PRAGMA integrity_check` 结果和临时文件清理状态。

准入要求为三轮零正确性失败、三轮均选择严格更小的有效候选、输出确定，且
生产管线门禁/取消测试通过。主机结果只用于开发，不替代真机准入。
