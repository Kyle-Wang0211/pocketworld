# PocketWorld 两层举报与审核闭环设计

**状态：** 用户于 2026-09-06 批准方案 B，并授权本次部署生产 Supabase；生产 iPhone 不在本次部署范围。

## 目标

把作品举报与账号举报合并到一条服务端受控管线，提供普通举报和复杂权益投诉两层入口，完成证据保全、优先级、审核、结果反馈和最小权限审核员访问。实现必须保持现有数据兼容，并把 Supabase 依赖收敛在仓储和服务端边界，便于以后迁移 PostgreSQL、对象存储与函数运行时到阿里云。

## 用户流程

### 举报入口

- 自己的账号和作品不显示举报入口；服务端也拒绝自举报。
- 他人作品的菜单进入统一举报页，并自动绑定作品、作者和举报入口来源。
- 他人主页的菜单进入同一举报页，但来源作品可以为空。
- 首屏显示两个独立入口：
  - 普通举报：适用于骚扰、诈骗、未成年人安全、色情低俗、暴力违法、虚假误导和其他问题。
  - 权益投诉：适用于冒充、隐私、肖像和知识产权问题。

### 普通举报

- 用户先选择稳定的一级原因代码，再填写可选补充说明。
- 补充说明最多 50 个 Unicode 字素簇；提示语为“请说明问题位于作品正面、背面、顶部或哪个画面”。
- 非敏感原因允许从系统照片选择器选择最多 3 张 JPG/PNG 证据。
- 涉及未成年人安全或色情低俗时，不允许用户重复上传材料；服务端冻结关联站内作品的模型、缩略图和预览视频供审核。

### 权益投诉

- 独立页面使用 500 个 Unicode 字素簇上限。
- 用户选择冒充、隐私、肖像或知识产权类别。
- 最多上传 3 张 JPG/PNG 证明材料，并标记材料类型：身份证明、权属证明、授权证明或其他证明。
- 身份证明不是强制字段；缺少材料时允许提交，审核员可通过用户可见反馈要求补充，避免客户端收集超出必要范围的身份信息。

### 提交和结果

- 举报正文先持久化，再顺序上传证据；部分图片失败时保留举报，并明确显示失败张数。
- 设置页增加“我的举报”。列表仅显示当前用户自己的举报编号、类别、创建时间、状态、用户可见处理说明和关联作品摘要。
- 状态为：待处理、审核中、已处理、未发现违规、需要补充材料。
- 内部审核备注绝不返回给举报人；审核员使用独立的公开反馈字段。

## 服务端数据与算法

### 统一提交接口

- 新的 `submit-report` Edge Function 取代客户端直接向 `reports` 插入。
- 请求包含 `kind`、`target_user_id`、可选 `source_work_id`、`reason`、`detail` 和入口来源。
- 服务端根据认证用户绑定 `reporter_id`，校验被举报账号存在、来源作品属于该账号、作品未删除、自举报被拒绝。
- 每个账号每小时最多提交 20 次；相同举报人、目标、来源作品和原因在 24 小时内只保留一条待处理举报，并返回既有举报编号。
- 旧版 `submit-user-report` 在过渡期调用同一核心逻辑；客户端对 `reports` 的直接 INSERT 权限被撤销。

### 字数和原因

- `kind = standard`：说明最多 50 个 Unicode 字符，数据库触发器以 PostgreSQL `char_length` 做最终上限；客户端用字素簇计数提供符合用户预期的提示。
- `kind = rights`：说明最多 500 个 Unicode 字符。
- 普通原因：`harassment_threat`、`spam_fraud`、`minor_safety`、`sexual_content`、`violence_illegal`、`misinformation`、`other`。
- 权益原因：`impersonation`、`privacy_ip`。
- 旧作品举报原因继续由数据库触发器映射到新代码，避免已安装旧客户端突然失效。

### 优先级与处理时限

优先级只决定人工队列顺序，不自动下架或封号：

| 原因 | 优先级 | 首次处理期限 |
|---|---:|---:|
| `minor_safety` | 100 | 24 小时 |
| `sexual_content`、`harassment_threat` | 80 | 24 小时 |
| `privacy_ip`、`impersonation`、`violence_illegal` | 60 | 72 小时 |
| 其他 | 40 | 7 天 |

- 数据库在插入时生成 `priority` 和 `due_at`，客户端不能覆盖。
- 审核队列按 `priority DESC, due_at ASC, created_at ASC` 排序。
- 超期状态由查询实时计算，不依赖后台定时任务。

### 证据与隐私

- 客户端把图片解码后重新编码，移除 EXIF/GPS，最长边不超过 2048 像素，单张不超过 5 MiB。
- Edge Function 再次校验真实文件签名、尺寸、元数据和张数，并生成不可预测的私有对象路径。
- 权益证明材料记录类型，但不保存原始文件名。
- 敏感举报冻结站内源作品；普通审核员只获得短时签名 URL，不获得对象存储主密钥。
- 举报人与审核员访问都写入审计日志；证据保留期和删除动作保留为可配置服务端策略。

## 审核员权限与审核台

- 新建 `moderator_accounts`，仅平台所有者可授予 `reviewer` 或 `lead` 角色。
- 审核员通过普通 Supabase Auth 登录；Edge Function 使用 JWT 校验角色，再在服务端以 service role 执行窄操作。
- 审核接口只允许列出队列、领取、进入审核、要求补充、驳回和确认处置；只有 `lead` 可以执行账号级处罚。
- 审核台不再接收或保存 service-role 密钥，使用审核员访问令牌。
- 每次状态变化记录审核员用户 ID、前后状态、公开反馈、内部备注和时间。
- 用户提交次数或举报数量不会自动触发处罚；作品下架和账号处罚必须是明确、可审计的人工动作。

## 阿里云迁移边界

- Flutter 页面只依赖 `ReportingRepository`，不直接依赖 Supabase 表结构。
- Supabase 实现负责 Auth JWT、Functions 调用和签名上传；未来阿里云实现可以替换为自建 API、RDS PostgreSQL、OSS 和函数计算。
- PostgreSQL 表和稳定原因代码可以迁移；Supabase Auth 用户、Storage 对象、RLS 和 Edge Functions 不能假定与阿里云 API 直接互通，需要导出、映射和重部署。
- 外部内容安全供应商通过服务端 `ModerationProvider` 边界接入。本次提供无外部调用的人工队列实现和明确接口，不虚构阿里/腾讯凭据或审核结果。

## 兼容迁移与生产部署

- 新迁移只新增列、表、函数和策略；历史举报原样保留并回填 `kind`、优先级和期限。
- 部署顺序为：数据库迁移 → 新函数 → 兼容旧函数 → 审核台 → 客户端代码。
- 在客户端尚未安装前，现有生产版本的旧作品举报仍能提交；服务端负责标准化与字数兼容。
- 生产部署前导出 schema 和受影响表的只读备份，记录 migration 列表和函数版本。
- 任一迁移、函数冒烟测试或旧客户端兼容测试失败即停止，不部署客户端，也不以删除数据方式回滚。

## 测试与验收

- 模型测试覆盖 50/500 字、Unicode 字素簇、原因与层级映射、三图和敏感证据禁传。
- Widget 测试覆盖作品入口、账号入口、两层页面、照片选择、部分上传失败、自己的对象无举报入口和“我的举报”。
- Deno 测试覆盖认证、自举报、作品归属、限流、24 小时去重、服务器生成优先级、证据类型和安全校验。
- SQL 合约测试覆盖撤销直接 INSERT、公开/内部备注隔离、安全 RPC、审核员角色、优先级和兼容回填。
- 审核台测试覆盖无 service-role 密钥、最小权限、队列排序、领取、结案、补充材料和审计记录。
- 生产 Supabase 部署后执行只读 schema/function 校验和专用测试账号冒烟测试；不使用用户日常账号制造真实违规内容。
- Flutter 相关测试、Deno 测试、静态分析和 iOS Release 构建必须通过。生产 iPhone 更新不属于本次验收，绝不卸载或覆盖 `com.kyle.PocketWorld`。

## 非目标

- 本次不签约或接入具体阿里云、腾讯云、网易易盾供应商。
- 本次不做自动封号、自动永久下架或基于举报数量的机器处罚。
- 本次不安装生产 iPhone，不清除任何本地作品、登录状态或 App Data Container。
